# 그릴링 기록: 판결문 쉬운 설명자료 제작 흐름

- 날짜: 2026-09-13
- 대상 기획: "AI로 만든 초안을 원문과 비교하고, 글·그림을 수정해서 최종 자료로 완성하는 과정을 한곳에서 돕는다" (① 판결문 업로드 → ⑥ 내보내기)
- 진행 방식: `grilling` 스킬의 라운드 방식. 설계 트리에서 선행 결정이 끝난 질문(frontier)을 라운드마다 한꺼번에 묻는다.
- **답변 방식**: 사용자가 "질문에 답하지 않을 테니 추천안으로 전부 채우라"고 위임했다. 그래서 모든 질문의 ➡️ 추천안을 **확정 답**으로 채택했다. 다음 라운드는 앞 라운드의 확정 답을 전제로 한다.
- 다음 산출물: 이 기록을 바탕으로 한 스펙 문서 [`docs/specs/judgment-easy-read.md`](../specs/judgment-easy-read.md)

## 사용자 지시 (질문 대상 아님)

1. 우리 저장소는 **프론트엔드만** 만든다. AI와 API는 별도 서버 프로젝트가 만든다. 이 저장소 안에 서버(Route Handler, 서버 액션으로 흉내 낸 API, AI 호출 등)를 절대 만들지 않는다.
2. 서버가 있다고 가정하고 **목(mock) API**로 개발한다. API 모양과 엔드포인트는 지금 고민하지 않는다. 서버가 구현되면 그때 맞춘다.
3. 첨부 스크린샷은 "어떤 기능이 필요한가"만 참고한다. 화면 구조와 레이아웃은 따라 하지 않고 더 낫게 새로 설계한다.
4. 라이브러리 후보(pdfcn, TanStack Query, zod, React Hook Form, zustand, Aceternity Multi Step Loader)는 짧게 적합성을 검토한 뒤 채택 여부를 정한다. React Hook Form은 과하면 뺀다.
5. 구현은 짧은 단위로 잘라서 한다.

## 설계 트리 개요

```
범위·사용자 ─┬─ 목 API 방식 ── 목 데이터(가상 판결문) ── 목 저장소
             ├─ URL 구조 ── 단계 진행 규칙
             ├─ 기기·셸·테마 ── 각 화면 레이아웃
             ├─ 원문 표현 단위 ─┬─ 사건 구조 모델 ── ② 구조 확인 화면
             │                  └─ 쉬운 자료 문서 모델 ─┬─ ③ 편집기(문장·근거·도구·수정안·용어·그림)
             │                                          ├─ ④ 검토(점검 항목·확인 체크리스트)
             │                                          └─ ⑤ 미리보기 ── ⑥ 내보내기(버전·링크·PDF)
             └─ 테스트 seam ── 구현 순서
```

## 사전 조사로 확인한 사실 (질문하지 않음)

조사는 하위 에이전트 두 개가 맡았다(Next.js 16 로컬 문서와 저장소 코드 / 라이브러리 적합성 웹 조사). 결정이 아니라 사실이라서 질문하지 않았다.

**저장소**

- Next.js 16.3.4(App Router, Turbopack 기본), React 19.2.8, Tailwind CSS v4, shadcn `base-vega`(Radix가 아니라 Base UI 기반), hugeicons, motion 13.2, pnpm 10, Node 22, TypeScript strict.
- 디자인 토큰: 토스증권 디자인 언어. `:root`는 밝은 회색·흰색, `.dark`는 딥 네이비. primary는 노란색. 머리 스크립트가 저장된 설정이나 OS 설정으로 `.dark`를 고른다(다크 고정이 아님).
- 이미 있는 UI: resizable(react-resizable-panels v4. `defaultSize`에 숫자를 넣으면 px, 문자열이면 %), toast(Base UI Toast, 아직 어디에도 마운트되지 않음), floating-toolbar, attachment, field, item, empty, tabs, dialog, alert-dialog, sheet, tooltip, popover, progress, skeleton 등.
- 없는 것: TanStack Query, zod, zustand, 테스트 도구, typecheck 스크립트, 이슈 트래커 설정(`docs/agents/`).

**Next.js 16에서 주의할 점** (`node_modules/next/dist/docs/` 기준)

- `params`와 `searchParams`는 Promise다. 서버 컴포넌트는 `await`, 클라이언트 컴포넌트는 `use()`로 읽는다. `PageProps<'/경로'>` 타입 헬퍼는 전역이다.
- `next/dynamic`의 `ssr: false`는 클라이언트 컴포넌트 안에서만 쓸 수 있다. 클라이언트 컴포넌트도 빌드 때 미리 렌더링되므로 렌더 중에 `window`를 건드리면 빌드가 깨진다.
- 정적 경로에서 `useSearchParams`를 쓰는 컴포넌트는 `<Suspense>`로 감싸야 한다. 개발 모드에서는 드러나지 않고 빌드 때 실패한다.
- `middleware`는 `proxy`로 이름이 바뀌었다. `cacheComponents`는 기본으로 꺼져 있다(켜지 않는다).
- 전체 화면 흐름과 상관없는 인쇄 전용 화면은 루트 레이아웃을 새로 만들지 말고 route group의 중첩 레이아웃으로 둔다(루트 레이아웃이 다르면 이동할 때 전체 새로고침이 일어난다).
- Vitest는 async 서버 컴포넌트를 테스트하지 못한다(우리 seam은 순수 함수라 상관없다).

## Round 1: 기반 결정

❓ **Q1** - **이번 구현 범위**: 기획 본문은 ①~⑥ 흐름을 말한다. 스크린샷에는 그 밖에 내 작업함, 공유 문서, 용어 사전, 설정, 카드뉴스 export, 공유 설정도 보인다. 어디까지 넣을까?

- (a) ①~⑥ 흐름만. 자료 1건을 끝까지 만드는 데모.
- (b) (a) + 작업함(목록, 이어서 하기, 삭제) + 독자용 읽기 화면.
- (c) (b) + 공유 문서, 용어 사전 페이지, 설정 페이지, 카드뉴스.

➡️ **(b)**. 작업함이 없으면 새로고침하거나 다시 들어왔을 때 작업을 이어갈 방법이 없다. 독자용 읽기 화면은 ⑥의 "읽기 화면으로 제공"이라는 산출물 자체라서 빠질 수 없다. 공유 문서(협업), 용어 사전 페이지, 설정 페이지, 카드뉴스는 기획 본문에 없으므로 뺀다.

---

❓ **Q2** - **사용자와 권한**: 제작자 로그인, 팀·조직, 권한, 독자 접근 제한이 필요한가?

➡️ **로그인과 권한은 없다.** 제작자는 한 명이라고 가정한다. 독자용 읽기 화면은 링크를 아는 사람이면 누구나 본다(공개 여부는 목 서버의 플래그로만 흉내 낸다). 인증은 서버가 생긴 뒤에 붙인다.

---

❓ **Q3** - **목 API를 두는 방식**: 서버가 있다고 가정한 목 API를 어떤 형태로 만들까?

- (a) **앱 안의 목 어댑터**: UI가 의존하는 타입 인터페이스(`ApiClient`)를 두고, 지연·실패를 흉내 내는 목 구현을 붙인다. 엔드포인트나 HTTP 개념이 없다.
- (b) **MSW**: 브라우저 service worker가 `fetch`를 가로챈다. 엔드포인트와 HTTP 요청·응답 모양을 지금 정해야 한다.
- (c) **Next.js Route Handler로 가짜 서버**: 우리 저장소에 서버를 만드는 일이라 지시 위반이다.

➡️ **(a)**. UI는 `ApiClient` 인터페이스만 알고, 서버가 준비되면 같은 인터페이스를 HTTP로 구현한 것으로 바꾼다. "엔드포인트는 지금 고민하지 않는다"는 지시와 가장 잘 맞는다. 목 구현은 한 곳에 모아 두고, 서버 연동 때 통째로 지울 대상으로 표시한다.

---

❓ **Q4** - **목 AI 결과를 흉내 내는 방법**: 사건 구조 분석, 초안 생성, 더 쉽게 바꾸기, 문장 나누기, 용어 설명, 그림 후보, 검토 점검은 모두 서버 AI의 몫이다. 목에서는 어떻게 결과를 줄까?

- (a) 어떤 파일이나 텍스트를 넣어도, 미리 만든 **가상 판결문 1건**의 결과를 준다.
- (b) 입력 텍스트를 실제로 분석하는 척하는 규칙 기반 추출.
- (c) 여러 건의 준비된 결과 중 무작위.

➡️ **(a)**. 분석과 초안은 준비된 결과(fixture)를 준다. 편집 중 요청(더 쉽게, 나누기, 용어 설명, 검토)은 fixture를 먼저 찾고, 없으면 목 폴더 안의 아주 단순한 규칙으로 그럴듯한 결과를 만든다(예: 쉼표나 "~고" 기준으로 나누기, 작은 쉬운 말 사전으로 바꾸기). 이 규칙은 제품 로직이 아니라 서버 연동 때 지울 목 코드다.
사건은 **가상의 임대차보증금 반환 사건**으로 한다(실존 인물·사건이 아님). 금액(보증금), 인물 관계(집주인·세입자), 주장과 판단의 구분, "돈을 주라고 결정" 대 "이미 돈을 받은 그림"이라는 기획의 검토 예시를 한 사건 안에서 모두 보여줄 수 있다.
업로드 화면에는 "데모 모드: 어떤 판결문을 올려도 샘플 사건으로 분석해요"라고 솔직하게 안내한다.

❓ **Q5** - **목 데이터 저장 위치**: 새로고침하면 작업이 사라져도 되나? 저장한다면 어디에?

- (a) 메모리만 (b) localStorage (약 5MB, 파일 저장이 어렵다) (c) IndexedDB

➡️ **(c) IndexedDB**. 올린 PDF 원본과 제작자가 직접 올린 그림(Blob)까지 새로고침 뒤에도 남는다. 얇은 key-value 래퍼 하나면 충분하다. 작업함에 "데모 데이터 초기화"를 둔다. IndexedDB를 쓸 수 없는 환경에서는 메모리 저장으로 대신한다.

❓ **Q6** - **URL 구조**: 단계를 한 페이지 안의 상태로 둘까, 단계마다 URL을 둘까?

➡️ **단계마다 URL을 둔다.**

| 경로                              | 화면                                              |
| --------------------------------- | ------------------------------------------------- |
| `/`                               | 작업함                                            |
| `/new`                            | ① 새 자료 만들기                                  |
| `/projects/[projectId]`           | 진행한 가장 먼 단계로 이동                        |
| `/projects/[projectId]/structure` | ② 사건 구조 확인                                  |
| `/projects/[projectId]/edit`      | ③ 쉬운 글·그림 편집 (선택한 문장은 쿼리로 딥링크) |
| `/projects/[projectId]/review`    | ④ 검토하기                                        |
| `/projects/[projectId]/preview`   | ⑤ 결과물 미리보기                                 |
| `/projects/[projectId]/export`    | ⑥ 내보내기                                        |
| `/read/[projectId]`               | 독자용 읽기 화면 (가장 최근에 내보낸 버전)        |
| `/showcase`                       | 기존 컴포넌트 쇼케이스 유지                       |

뒤로 가기, 새로고침, "검토 항목 → 편집기의 그 문장으로 이동" 같은 딥링크가 자연스러워진다.

❓ **Q7** - **대상 기기**: 3단 편집기는 넓은 화면이 필요하다. 반면 독자는 휴대폰으로 볼 가능성이 크다.

➡️ **제작 화면은 데스크톱 우선, 독자 화면은 모바일 우선.**

- 제작 화면(①~~⑥): 1280px 이상에서 최적. 1024~~1279px에서는 원문 패널을 접어서 쓴다. 1024px 미만에서는 "넓은 화면에서 편집해 주세요"라고 안내한다.
- 독자용 읽기 화면: 모바일 우선 반응형.
- 인쇄물: A4 세로.

❓ **Q8** - **앱 셸(내비게이션)**: 스크린샷처럼 왼쪽 사이드바를 둘까?

➡️ **전역 사이드바는 두지 않는다.** 편집기에 가로 폭을 최대한 준다. 프로젝트 안에서는 상단 바 한 줄에 로고(작업함으로 이동), 자료 제목, 단계 표시(1~6), 저장 상태, 다음 단계 버튼을 둔다. 작업함과 새 자료 화면은 가운데 정렬한 단일 컬럼이다.

❓ **Q9** - **테마**: 지금 디자인 시스템에는 밝은 테마(토스증권 회색·흰색)와 네이비 다크 테마가 있다. 저장된 설정이나 OS 설정에 따라 머리 스크립트가 고른다. 판결문과 쉬운 자료는 긴 글이고, 독자 화면과 인쇄물은 흰 종이가 어울린다. 결과물 면도 사용자 테마를 따라 어두워져야 할까?

➡️ **도구는 사용자 테마를 따르고, 결과물은 항상 종이.** 제작 도구의 틀(상단 바, 패널, 버튼)은 기존 밝은·다크 테마를 그대로 따른다. 결과물이 보이는 면(편집기 가운데 캔버스, 미리보기, 독자 화면, 인쇄물)은 테마와 상관없이 항상 밝은 "종이" 모양으로 그린다. 제작자가 독자와 같은 모양을 보면서 편집하게 하려는 것이다. 종이 면은 기존 토큰 체계 안에 범위 한정 클래스로 추가하고, 컴포넌트에 색을 직접 박지 않는다. 독자 화면은 제작자의 테마 설정을 따르지 않는다.

❓ **Q11** - **원문(판결문)을 다루는 단위**: "문장을 누르면 원문 강조", "구조 항목의 원문 근거"를 하려면 원문을 어떤 단위로 다룰지 정해야 한다.

❓ **Q17** - **PDF: pdfcn과 원본 PDF 보기**: pdfcn을 PDF 작업에 쓸까? 왼쪽 원문 패널에 올린 PDF 원본을 보여 줄까?

➡️ **pdfcn은 이번에 쓰지 않고, 원본 PDF 보기도 뺀다.**

- pdfcn은 PDF를 **만드는** 도구라서 원문 보기·강조·추출에는 도움이 되지 않는다.
- PDF 출력에 쓰기에도 이르다. 1.0 이전이고 공개된 지 몇 주밖에 안 됐다. 한글 폰트를 직접 등록해야 하고, 폰트에 없는 글자가 하나만 있어도 내보내기가 실패한다. 독자 화면과 따로 노는 두 번째 레이아웃(인라인 스타일)을 만들어야 해서 "미리보기와 인쇄물이 같은 모양"을 보장하기 어렵다. PDF 출력 방식은 뒤 라운드(Q58)에서 따로 정한다. 서버 쪽 PDF 생성을 검토할 때 다시 볼 만하다.
- 원본 PDF 보기를 빼는 이유: 데모 모드에서는 무엇을 올려도 샘플 사건으로 분석하므로(Q4), 올린 PDF를 보여 주면 분석 결과와 **다른 문서**가 나란히 보여 혼란스럽다. 근거 강조는 추출 텍스트로 충분하다. 서버가 붙은 뒤 원본 보기가 필요하면 pdf.js 기반 뷰어(react-pdf 등)를 따로 검토한다.
- 그래서 Q5의 IndexedDB에는 PDF 파일 자체를 넣지 않고 파일 이름·크기 같은 정보만 저장한다. 직접 올린 그림은 그대로 저장한다.

❓ **Q19** - **① 입력 방식과 제한**: 판결문을 어떤 형태로, 어떤 제한으로 받을까? 자료 제목도 입력받을까?

❓ **Q20** - **① 설정 항목과 기본값**: 기획은 "성인 존중 문체, 인물 호칭, 그림 사용 여부 정도만" 설정한다고 한다. 스크린샷의 "대상 독자" 선택도 둘까? 설정을 드롭다운으로 보여 줄까?

➡️ **설정은 세 가지만, 대상 독자 선택은 두지 않는다**(이 제품의 독자는 발달장애가 있는 성인으로 고정). 드롭다운 대신 **예시 문장이 보이는 선택 카드**로 보여 준다. 고르는 순간 결과물이 어떻게 달라지는지 알 수 있어야 한다.

| 설정      | 선택지 (기본값 굵게)                                                                   | 카드 속 예시                                                           |
| --------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |

❓ **Q21** - **사건 구조 데이터 모델**: ②에서 AI가 정리하고 제작자가 고치는 "사건 구조"에 무엇을 담을까? 특히 "당사자가 주장한 내용"과 "법원이 인정·결정한 내용"이 섞이지 않게 하려면 모델에서 어떻게 구분할까?

➡️ **주장과 법원의 판단·결정을 서로 다른 목록으로 나눈다.** 한 목록 안에서 "종류" 필드로만 구분하지 않는다. 섞임을 고치는 일은 "항목을 다른 목록으로 옮기기"라는 눈에 보이는 동작이 된다.

- **사건 정보**: 사건명, 사건번호, 법원, 선고일
- **등장인물**: 원문 표기(예: 원고 A), 법적 지위(원고·피고 등), 호칭(설정값 기본, 인물별 변경), 쉬운 역할 설명(예: 집을 빌린 사람), 근거
- **핵심 사실**: 종류(금액·날짜·기간·기타), 이름(예: 임대차보증금), 값(예: 1억 원), 근거. 검토 단계에서 숫자 대조의 기준이 된다.
- **주장**: 누구의 주장인지(인물), 내용, 근거
- **법원의 판단**: 내용, 어느 주장에 대한 판단인지(없을 수 있음), 받아들임·받아들이지 않음·일부만 받아들임·해당 없음, 근거
- **최종 결정(주문)**: 내용, 근거
- 모든 항목 공통: ID, 근거 목록, AI의 "확인 필요" 표시(이유 문구 포함, 여러 개 가능)

❓ **Q22** - **쉬운 설명자료 문서 모델**: 편집기와 독자 화면, 인쇄물이 함께 쓰는 문서를 어떤 구조로 둘까?

➡️ **구획 → 카드 → 문장.** 여기에 문서 단위의 용어 풀이와 그림이 붙는다.

- **구획**: 기획이 정한 독자 읽기 순서를 그대로 고정한다. ① 누가 나오나요 → ② 무엇을 결정했나요 → ③ 왜 그렇게 결정했나요 → ④ 어려운 말 풀이. 구획 제목은 초안이 채우고 제작자가 고칠 수 있다. 구획을 추가하거나 순서를 바꾸지는 않는다.
- **카드**: 그림 0~1개와 문장 1개 이상. 카드에는 **역할**이 있다: 인물 소개(어느 인물인지), 배경 사실, 주장(누구의 주장인지), 법원의 판단, 최종 결정. 주장과 판단의 구분은 문장이 아니라 **카드 역할**이 맡는다. 카드 머리 라벨("A씨가 한 말", "법원의 생각")도 역할에서 나온다.
- **문장**: 텍스트, 근거 목록, 출처(AI 초안 / AI 수정안 적용 / 직접 작성), 원문 대조 여부. 쉬운 글 원칙에 따라 한 문장은 한 줄에 하나씩 보여 준다.
- **용어 풀이**: 용어, 쉬운 설명. 문장 안의 위치를 저장하지 않고, 화면에 그릴 때 글자 일치로 찾는다(문장을 고쳐도 깨지지 않는다).
- **그림**: 주소, 대체텍스트, 의미 설명(무엇을 나타내는 그림인지. 글과 그림이 맞는지 점검할 때 쓴다), 출처(그림 목록 / 직접 올림).
- 문서 전체: 제목, 수정 번호(저장할 때마다 1씩 증가), 초안을 만들 때 기준으로 삼은 사건 구조의 수정 번호.

④ 어려운 말 풀이 구획은 카드가 아니라 용어 풀이 목록으로 그린다.

## Round 3: 화면 골격과 흐름 규칙

❓ **Q23** - **폼: React Hook Form**: ① 입력 폼과 ② 사건 구조 편집에 RHF를 쓸까?

❓ **Q24** - **단계 진행 규칙**: 스텝(1~6)을 자유롭게 오갈 수 있게 할까, 순서대로만 갈 수 있게 할까? 각 단계의 "완료"는 무엇일까?

➡️ **필요한 데이터가 있으면 자유롭게 오간다.** 완료 상태는 저장된 데이터에서 계산하고, 따로 저장하지 않는다.

| 단계        | 들어갈 수 있는 조건                                                          | 완료 표시                                 |
| ----------- | ---------------------------------------------------------------------------- | ----------------------------------------- |
| ① 올리기    | 새 자료일 때만(만든 뒤에는 완료 상태로만 표시, 누르면 올린 파일과 설정 요약) | 분석 완료                                 |
| ② 사건 구조 | 분석 완료                                                                    | 제작자가 구조를 확정하고 초안을 만듦      |
| ③ 편집      | 초안 있음                                                                    | (완료 개념 없음)                          |
| ④ 검토      | 초안 있음                                                                    | 검토 완료이고, 그 뒤로 문서가 바뀌지 않음 |
| ⑤ 미리보기  | 초안 있음                                                                    | (완료 개념 없음)                          |
| ⑥ 내보내기  | 초안 있음                                                                    | 마지막으로 내보낸 결과가 현재 문서와 같음 |

검토를 끝낸 뒤 문서가 바뀌면 ④는 "검토 후 수정됨"으로 바뀐다. 이 계산은 도메인 모듈의 순수 함수로 두고 테스트한다.

❓ **Q25** - **② 화면 구성**: 기획은 "제작자가 이 내용을 원문과 비교하고 잘못된 부분을 수정"한다고 한다. 비교가 핵심인데 구조만 한 줄로 늘어놓을까?

➡️ **왼쪽 원문, 오른쪽 사건 구조의 2단 분할.**

- 왼쪽은 ③과 같은 원문 뷰어 컴포넌트를 쓴다.
- 오른쪽은 위에서 아래로 사건 정보 → 등장인물 → 핵심 사실 → 당사자가 주장한 내용 → 법원이 판단한 내용 → 법원의 최종 결정 순서다. 상단에 구획 바로가기와 "확인 필요 N개"를 둔다.
- **주장 영역과 법원 영역은 서로 다른 면**으로 나눈다. 주장 영역에는 인물별 색 점, 말풍선 아이콘, "당사자가 주장한 내용이에요. 법원이 인정한 사실이 아니에요"라는 머리말을 둔다. 법원 영역에는 법원 아이콘과 "법원이 판단하고 결정한 내용이에요"라는 머리말을 둔다. 색만으로 구분하지 않고 아이콘과 글자를 함께 쓴다.
- 항목을 선택하면 왼쪽 원문이 근거로 스크롤하고 강조한다.
- AI가 "확인 필요"로 표시한 항목은 경고 색 테두리와 이유 문구를 보여 준다.

❓ **Q26** - **② → 초안 만들기 조건**: 구조가 어떤 상태여야 초안을 만들 수 있을까?

➡️ **막는 조건과 알리는 조건을 나눈다.**

- 막는 조건(버튼 비활성 + 이유 표시): 인물 1명 이상, 최종 결정 1개 이상, 모든 주장에 인물 지정, 빈 문구 없음, **"원문과 비교해 확인했어요" 체크**.
- 알리는 조건: 남은 "확인 필요" 표시. 버튼을 누르면 "확인 필요 2개가 남았어요. 그래도 초안을 만들까요?"라고 묻는다.
- 체크박스는 제작자가 원문과 비교했다는 사실을 한 번 더 스스로 확인하게 하는 장치다.

❓ **Q27** - **초안을 만든 뒤 구조나 설정을 바꾸면**: 이미 편집한 초안은 어떻게 될까?

➡️ **초안은 자동으로 바뀌지 않고, 다시 만들기는 제작자가 고른다.**

- 초안이 있는 상태에서 ②를 열면 "초안이 이미 있어요. 여기서 고친 내용은 초안을 다시 만들어야 반영돼요"라고 안내한다.
- 구조를 고치거나 [자료 설정](② 상단 대화상자)에서 설정을 바꾸면 문서는 그대로 두고 "구조가 초안보다 새로워요" 상태가 된다.
- 편집기 상단에 "사건 구조가 바뀌었어요. [초안 다시 만들기]" 배너를 띄운다. 다시 만들기는 편집 내용을 덮어쓰므로 확인 대화상자에 "지금까지 손본 문장 N개가 사라져요"라고 적는다.
- 다시 만들지 않으면 검토 단계에 "초안을 만든 뒤 사건 구조가 바뀌었어요" 항목이 뜬다.

❓ **Q28** - **③ 편집기 레이아웃**: 기획은 왼쪽 원문, 가운데 쉬운 설명자료, 오른쪽 편집 도구와 확인 항목을 배치한다고 한다. 각 패널을 어떻게 구성할까?

➡️ **크기를 조절할 수 있는 가로 3단.** 크기는 브라우저에 기억한다.

| 원문 (기본 30%, 접기 가능)                          | 쉬운 자료 캔버스 (기본 44%)                                                                                                                      | 문장 도구 (기본 26%, 최소 320px) |
| --------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------- |
| 구획 바로가기(주문·청구취지·이유 소제목), 근거 강조 | 종이 면. 독자 화면과 같은 카드 모양(그림 왼쪽, 문장은 한 줄에 하나). 위에 구획 목차(1~4)와 문서 제목. 카드 머리에 역할 라벨. 문장 옆에 상태 표시 | 선택에 따라 바뀜                 |

문장 도구 패널:

- **아무것도 선택하지 않았을 때**: 문서 요약. 진행 상황, 근거 없는 문장 수, 마지막 점검 결과 요약, 용어 목록.
- **문장을 선택했을 때**: ① 선택한 문장과 도구 5개(직접 수정하기·더 쉽게 바꾸기·문장 나누기·용어 설명 추가·그림 바꾸기) ② 도구 결과(수정안 비교, 용어 입력, 그림 후보) ③ 원문 근거 인용 ④ 이 문장의 점검 항목(마지막 점검 기준).

스크린샷의 "원문 위치 보기" 같은 별도 버튼은 두지 않는다. 문장을 선택하기만 하면 원문이 따라 움직인다.

❓ **Q29** - **그림 바꾸기**: 그림은 무엇을 기준으로 바꾸고, 어떤 선택지를 줄까?

➡️

- 그림은 카드 단위다. 문장을 선택한 상태에서 [그림 바꾸기]를 누르면 그 문장이 속한 카드의 그림을 바꾼다.
- 선택지: 서버가 카드 내용에 맞춰 준 그림 후보 4~6개(후보마다 의미 설명), [그림 없이], [내 그림 올리기](PNG·JPG·SVG, 2MB 이하).
- 후보를 고르면 지금 그림과 나란히 비교하고, 대체텍스트(후보의 기본값을 채움, 고칠 수 있음)를 확인한 뒤 [적용]한다.
- 직접 올린 그림은 제작자가 의미 설명과 대체텍스트를 적는다. 대체텍스트는 필수다.
- 설정이 "글만"이면 그림 도구와 그림 칸을 모두 숨긴다.

❓ **Q30** - **자동 저장과 되돌리기**: 저장 버튼을 둘까? 되돌리기는 어디까지?

➡️

- **저장 버튼은 없고 자동 저장한다.** 편집 사본이 바뀌고 1초 동안 추가 변경이 없으면 저장한다. 상단 바에 "저장 중… / 저장됨 / 저장 못 함 [다시 시도]"를 보여 준다. 저장 안 된 변경이 있는데 탭을 닫으려 하면 브라우저 경고를 띄운다.
- **되돌리기는 편집기 세션 동안 최대 50단계.** 도구 적용 1번, 직접 수정 확정 1번, 문장·카드 추가·삭제·이동 1번이 각각 1단계다. ⌘Z / ⇧⌘Z와 상단 바 버튼으로 한다. 새로고침하면 이력은 사라지지만 저장된 문서는 남는다. 되돌린 결과도 자동 저장된다.

❓ **Q31** - **긴 AI 작업의 로딩 UX**: Aceternity 로더를 어디에 쓰고, 단계는 무엇으로 넘기며, 취소·실패는 어떻게 할까?

➡️

- 전체 화면 로더는 **사건 구조 분석(① → ②)과 초안 생성(② → ③) 두 곳에만** 쓴다. 둘 다 오래 걸릴 수 있고, 끝나기 전에는 다음 화면으로 갈 수 없다.
- 분석 단계 문구: 판결문을 읽고 있어요 → 사건 정보를 찾고 있어요 → 등장인물을 정리하고 있어요 → 주장과 법원의 판단을 나누고 있어요 → 최종 결정을 확인하고 있어요.
- 초안 단계 문구: 사건 구조를 확인하고 있어요 → 쉬운 말로 바꾸고 있어요 → 한 문장에 한 내용만 담고 있어요 → 어려운 말 풀이를 만들고 있어요 → 그림을 고르고 있어요.
- 서버가 진행률을 주지 않는다고 가정한다. 단계는 시간(약 1.5초 간격)으로 넘기고, 마지막 단계에 닿으면 응답이 올 때까지 멈춘다. 응답이 오면 모든 단계를 완료로 표시하고 잠깐 뒤 다음 화면으로 간다.
- [취소]를 누르면 요청을 중단하고 원래 화면에 머문다. 목도 중단 신호를 존중한다.
- 실패하면 로더를 닫고 그 화면에 오류 상자("분석하지 못했어요" + [다시 시도])를 띄운다.
- 나머지 AI 요청(더 쉽게, 나누기, 용어, 그림 후보, 점검)은 화면을 막지 않는다. 결과가 들어갈 자리에 스켈레톤이나 작은 스피너를 둔다.
- 목 지연 시간: 분석 약 6초, 초안 약 7초, 편집 도구 1초 안팎, 점검 약 2초, 일반 조회 0.3초 안팎.

❓ **Q32** - **원문 뷰어 표시**: 원문 PDF 보기를 뺐으니(Q17), 추출 텍스트를 어떻게 보여 줄까?

➡️

- 추출 텍스트를 문단 단위로 보여 준다. 구획 제목은 굵게, 주문의 번호 목록은 들여쓰기해서 판결문 서식을 살린다. 본문 폭은 읽기 좋은 너비로 제한한다.
- 상단 구획 바로가기: 주문 / 청구취지 / 이유(1. 기초사실, 2. 당사자의 주장, 3. 판단, 4. 결론). 스크롤 위치에 따라 지금 구획을 표시한다.
- PDF에서 온 문단이면 옆에 작은 쪽 번호를 붙인다.
- 근거 강조는 형광펜 모양 배경이다. 여러 근거 중 지금 보고 있는 근거는 더 진하게 칠한다.
- 원문은 읽기 전용이다. 글자를 드래그해 선택하는 것만 허용한다(근거 편집에 쓸 수 있게).
- 원문 안 검색은 범위 밖이다(브라우저 찾기로 충분).

❓ **Q33** - **결과물 렌더러를 하나로 둘까**: 편집 캔버스, 미리보기, 독자 화면, 인쇄물이 같은 카드·문장 모양을 보여야 한다. 각각 따로 만들까?

➡️ **하나의 "자료 렌더러"를 네 곳이 함께 쓴다.** 카드, 문장, 용어 밑줄, 역할 라벨, 안내 문구의 모양을 한 곳에서 정하고, 쓰임새(편집 / 읽기 / 인쇄)에 따라 상호작용과 치수만 달라진다. 선택, 상태 점, 편집 입력칸은 편집 모드에서만 붙는다. 그래야 "편집기에서 본 모양 = 독자가 보는 모양"이 유지된다. 편집 캔버스는 넓은 카드(그림 왼쪽), 독자 화면은 반응형(좁으면 그림이 위), 인쇄는 A4 고정 비율이다.

## Round 4: 편집 상호작용과 결과물 모양

❓ **Q34** - **② 항목 편집 동작**: 제작자가 구조를 고칠 때 어떤 동작이 필요할까?

➡️

- 모든 문구는 제자리에서 편집한다(누르면 입력칸).
- 인물, 핵심 사실, 주장, 판단, 결정을 모두 추가·삭제할 수 있다.
- **옮기기**: 주장 ↔ 법원의 판단 ↔ 최종 결정 사이로 항목을 옮긴다. 주장으로 옮길 때는 인물을 고른다. 옮겨도 근거는 유지된다. "섞임"을 고치는 핵심 동작이다.
- 주장의 인물 바꾸기. 판단이 어느 주장을 다루는지와 받아들임 여부 고르기.
- 근거: 항목의 근거 목록을 보고, 원문에서 드래그해 추가하고, 뺀다(③ 편집기와 같은 방식).
- "확인 필요" 표시는 내용을 고치거나 [확인했어요]를 누르면 사라진다.
- 인물 호칭은 설정값으로 채워지고 인물마다 바꿀 수 있다.
- 편집 내용은 자동으로 임시 저장한다. 화면을 나갔다 와도 남아 있다.

❓ **Q35** - **문장 선택과 원문 연결**: "가운데 문장을 누르면 왼쪽에서 해당 원문이 강조"를 구체적으로 어떻게 할까?

➡️

- 문장을 누르면 선택한다(한 번에 하나). 선택한 문장 ID는 URL 쿼리에 남긴다(검토 화면에서 딥링크로 들어올 수 있게).
- 키보드: ↑/↓ 이전·다음 문장, Enter 직접 수정, Esc 선택 해제, ⌘Z / ⇧⌘Z 되돌리기·다시 하기.
- 선택하면 원문 패널이 첫 근거로 부드럽게 스크롤하고, 그 문장의 근거 범위를 모두 강조한다. 근거가 여러 개면 "근거 1/2 ‹ ›"로 오간다.
- 역방향: 원문의 강조 범위를 누르면 그 범위를 근거로 쓰는 문장을 선택한다.
- 근거가 없는 문장은 캔버스와 패널 모두에 "원문 근거 없음"을 표시한다.
- 카드 머리나 그림을 누르면 카드를 선택한다. 이때 패널은 카드 도구(그림 바꾸기, 문장 추가, 카드 역할 보기)를 보여 준다.

❓ **Q36** - **문장별 원문 대조 표시**: "AI 초안을 원문과 비교한다"는 제품의 핵심 가치를 편집기에서 어떻게 보이게 할까?

➡️ **문장마다 "원문과 대조했음" 상태를 두고, 진행률로 보여 준다.**

- AI 초안 문장과 AI 수정안을 적용한 문장은 "대조 전"이다.
- 제작자가 직접 고친 문장은 "대조 완료"로 본다.
- 도구 패널의 [대조했어요] 버튼, 또는 **⌘Enter(대조 완료로 표시하고 다음 문장으로 이동)**. 원문과 문장을 보고 ⌘Enter만 누르며 끝까지 훑을 수 있다.
- 상단 바에 "원문 대조 18/30". 캔버스에서는 대조 전 문장 옆에 옅은 점을 찍고, 대조가 끝난 문장은 표시하지 않는다(결과물 모양을 해치지 않게).
- 근거 목록이 바뀌어도 대조 상태는 그대로다.
- 대조가 덜 끝났다고 검토 완료나 내보내기를 막지는 않는다(Q60, Q61). 대신 남은 수를 계속 보여 준다.

❓ **Q37** - **직접 수정과 편집 범위**: 직접 수정은 어떻게 하고, 문장·카드 단위 편집은 어디까지 허용할까?

➡️

- 직접 수정: 캔버스 제자리 입력칸(높이 자동). Enter 또는 바깥 클릭 = 적용, Esc = 취소. 문장 안 줄바꿈은 없다(두 문장이 필요하면 "문장 나누기"나 "문장 추가").
- 문장: 아래에 추가, 삭제, 같은 카드 안에서 위·아래로 이동.
- 카드: 추가(구획에 맞는 역할 선택), 삭제(확인 대화상자), 같은 구획 안에서 위·아래로 이동. 구획을 넘어가는 이동은 없다.
- 끌어다 놓기는 범위 밖이고, 메뉴와 버튼으로 한다.
- 문서 제목과 구획 제목은 제자리에서 고친다.

❓ **Q38** - **AI 수정안 비교와 적용(더 쉽게 바꾸기)**: "AI 수정안은 바로 덮어쓰지 않고, 수정 전후를 보고 제작자가 적용"을 어떻게 보여 줄까?

➡️

- [더 쉽게 바꾸기] → 도구 결과 영역에 로딩 → 수정안 최대 3개(1/2/3 탭).
- 수정안마다 전(지금 문장)과 후를 위아래로 두고 **어절 단위**로 차이를 강조한다(지운 부분 취소선, 새로 넣은 부분 밑줄과 배경). 글자 단위는 조사 변화 때문에 너무 잘게 쪼개져 읽기 어렵다.
- **숫자가 달라지면 강하게 경고**한다: "숫자가 바뀌었어요: 1억 원 → 1,000만 원". 차이 표시를 돕는 화면 기능이다.
- 버튼: [적용] / [고쳐서 적용](수정안을 입력칸으로 열어 손본 뒤 적용) / [다시 제안] / [닫기].
- 적용하면 출처가 "AI 수정안"이 된다. 근거는 유지된다. 되돌리기 1단계다.
- 적용하기 전에는 캔버스 문장이 바뀌지 않는다. 대신 캔버스의 그 문장에 "수정안 보는 중" 점선 테두리를 친다.
- 수정안을 열어 둔 채 다른 문장을 선택하면 수정안은 닫힌다.

❓ **Q39** - **용어 설명 추가**: 어떤 용어를 고르고, 어디에 보여 줄까?

➡️

- [용어 설명 추가] → 서버가 선택 문장에서 풀이가 필요해 보이는 후보 용어를 칩으로 제시한다. 제작자가 문장 안의 글자를 직접 드래그해 골라도 된다.
- 용어를 고르면 쉬운 설명 초안이 입력칸에 채워지고, 제작자가 고친 뒤 [추가]한다.
- 이미 등록된 용어면 "이미 풀이가 있어요"와 함께 설명 편집으로 이어진다.
- 등록한 용어는 캔버스의 모든 문장에서 점선 밑줄로 표시한다. 누르면 설명을 보고 고칠 수 있다.
- ④ 어려운 말 풀이 구획은 용어가 문서에 처음 나오는 순서로 자동 정렬한다. 더 이상 어느 문장에도 나오지 않는 용어는 "문장에 없음"으로 표시하고 검토 항목이 된다.
- 문서 요약 패널에서 전체 용어 목록을 보고 고치거나 지운다.

❓ **Q40** - **목 그림 에셋**: 서버가 줄 그림을 목에서는 무엇으로 대신할까?

➡️ **저작권 걱정 없는 자체 픽토그램 장면.** 이미 의존성에 있는 hugeicons 무료 아이콘(MIT 라이선스, 확인함)을 조합해 단순한 장면 SVG를 만든다(사람과 집, 사람→돈→사람, 법원과 저울, 계약서, 달력 등). 개발용 스크립트로 생성해 정적 파일로 두고, 20장 안팎으로 한다. 그림마다 의미 설명과 기본 대체텍스트를 붙인다. 기획의 불일치 예시를 시연하려고 "이미 돈을 받은 모습"과 "돈을 돌려주라고 결정하는 모습"을 둘 다 만든다. 서버를 연동할 때 목 코드와 함께 지운다.

❓ **Q41** - **근거 편집**: AI가 연결한 근거가 틀렸거나 없을 때 제작자가 어떻게 고칠까?

➡️ 원문 패널에서 글자를 드래그해 선택하면, 선택한 문장(또는 ②의 구조 항목)이 있을 때 선택 영역 옆에 "선택한 문장의 근거로 추가" 버튼이 뜬다. 한 번에 한 문단 안에서만 고를 수 있고, 여러 문단은 여러 번 추가한다. 도구 패널의 원문 근거 인용마다 [빼기]가 있다.

❓ **Q42** - **상태를 어디에 둘지**: Q14(TanStack Query), Q15(zod), Q16(zustand), Q23(React Hook Form)의 결과를 합치면 상태별로 어디에 두어야 할까?

➡️

| 상태                                                                           | 둘 곳                          |
| ------------------------------------------------------------------------------ | ------------------------------ |
| 목 API에서 온 데이터                                                           | TanStack Query 캐시            |
| ②·③의 편집 사본, 선택, 열린 수정안, 되돌리기 이력                              | 화면마다 만드는 zustand 스토어 |
| 딥링크가 필요하거나 다시 열었을 때 유지할 선택(선택한 문장, 화면 안의 탭·필터) | URL 쿼리                       |
| 한 컴포넌트 안에서 끝나는 입력(① 폼, 대화상자)                                 | React 로컬 상태                |
| 패널 크기 같은 기기별 화면 설정                                                | localStorage                   |

흐름은 이렇다. 화면이 열리면 쿼리 데이터로 편집 사본 스토어를 한 번 초기화한다 → 편집은 스토어에서 한다 → 자동 저장 mutation이 목 서버에 반영한다 → 성공하면 쿼리 캐시를 저장한 값으로 바로 갱신한다(다시 불러오지 않음). 제작자가 한 명이므로 저장 충돌은 다루지 않는다.

❓ **Q43** - **독자 읽기 화면**: 기획의 "누가 나오는지 → 무엇을 결정했는지 → 왜 그렇게 결정했는지 → 어려운 말 설명" 순서를 발달장애가 있는 성인 독자에게 어떻게 보여 줄까?

➡️

- 순서: 표지 → 1 누가 나오나요 → 2 무엇을 결정했나요 → 3 왜 그렇게 결정했나요 → 4 어려운 말 풀이 → 마침.
- **기본은 한 구획씩 넘겨 보기.** 한 화면의 정보량을 줄이려는 것이다. 아래에 큰 [이전]/[다음] 버튼과 "2 / 4" 진행 표시를 두고, ←/→ 키도 쓴다. [한 번에 모두 보기]로 바꿀 수 있다.
- 표지: 제목, 한 줄 설명, 작은 사건 정보(법원·사건번호·선고일), 안내 문구 상자, [읽기 시작].
- 카드: 좁은 화면은 그림 위·글 아래, 640px 이상은 그림 왼쪽·글 오른쪽. 문장은 한 줄에 하나.
- 글자: 기본 20px, 행간 1.7, 어절 단위 줄바꿈(`word-break: keep-all`). [가] 버튼으로 보통·크게·아주 크게 3단계를 고르고 기기에 기억한다.
- 카드 머리 라벨은 아이콘과 글자로 보여 준다: "A씨가 한 말"(말풍선), "법원의 생각"(저울), "법원이 정한 것"(법봉). 독자도 주장과 판단을 구분할 수 있게 하려는 것이다.
- 어려운 말: 점선 밑줄 단어를 누르면 설명이 뜬다(넓은 화면은 팝오버, 좁은 화면은 아래에서 올라오는 시트). 4구획에 모두 모은다.
- 마침 화면: 안내 문구를 다시 보여 주고 [처음으로].
- 없거나 공개하지 않은 자료: "지금은 볼 수 없는 자료예요".
- 제작 도구의 상단 바와 테마 설정은 보이지 않는다.

❓ **Q44** - **인쇄용 레이아웃**: A4 인쇄물은 어떤 모양일까?

➡️

- A4 세로, 쪽마다 여백 16mm.
- 1쪽 표지: 제목, 한 줄 설명, 사건 정보, 안내 문구 상자.

- 어려운 말 풀이는 "용어 | 설명" 표.
- 흑백으로 인쇄해도 구분되도록 역할 라벨은 색이 아니라 아이콘과 글자로 표시한다.

❓ **Q45** - **로딩·오류 상태와 목 실패 흉내**: 실패와 빈 상태를 어떻게 다룰까?

- 아직 들어갈 수 없는 단계는 앞 단계로 안내하는 빈 상태 화면이다(예: "아직 초안이 없어요 [사건 구조 확인으로]"). 없는 프로젝트와 없는 주소는 앱 모양의 404 화면이다.

❓ **Q46** - **문장 나누기 적용 규칙**: 한 문장이 여러 문장이 될 때 근거·출처·대조 상태는?

❓ **Q47** - **수정안 차이 계산**: 어절 단위 차이(Q38)와 숫자 변경 경고를 무엇으로 계산할까?

➡️ **외부 diff 라이브러리 없이 도메인 모듈에 직접 둔다.** 문장이 짧아서(대개 60자 이하) 어절 단위 LCS로 충분하고 비용도 없다. 어절 나누기 규칙(띄어쓰기 기준, 문장부호 분리)을 우리가 정할 수 있고, seam에서 테스트된다. 숫자 변경 감지도 같은 모듈에 둔다. 두 문장의 숫자 표현("1억 원", "1,000만 원", "2022년 3월 1일")을 뽑아 비교하는 화면 보조 기능이며, 점검 판단은 서버 몫이다.

❓ **Q48** - **검토 결과 모델**: ④에서 무엇을 보여 줄까?

➡️ 성격이 다른 세 가지를 함께 보여 준다.

1. **자동 점검 항목**(서버 AI, 지금은 목): 분류, 수준(확인 필요 / 살펴보기), 제목, 설명, 대상(문장·카드·그림·용어·문서), 비교 근거(쉬운 문장, 원문 인용, 구조 값, 그림), 제안 수정안(있을 때만), 상태(남음 / 해결됨 / 문제없음 확인과 메모).
2. **원문 대조 현황**: Q36의 문장별 대조 상태에서 계산한다(서버를 부르지 않음).

❓ **Q49** - **쪽 나누기 방식**: 미리보기의 쪽과 실제 인쇄 쪽이 같아야 한다. 어떻게 나눌까?

➡️ **화면에서 쪽을 직접 나눈다.** A4 본문 폭에서 카드 높이를 재고, 쪽에 차례로 채운다. 구획은 새 쪽에서 시작하고, 카드는 쪼개지 않는다. 한 쪽보다 큰 카드는 그 쪽에 혼자 둔다. 이렇게 만든 쪽 구성을 미리보기와 인쇄가 함께 쓰므로, 미리보기의 "7쪽"이 실제 인쇄 쪽수와 같다. 브라우저의 CSS 쪽 나눔(@page 여백 상자 등)은 화면에서 미리 볼 수 없어서 기대지 않는다. 채우기 계산은 순수 함수로 두고 seam에서 테스트한다.

❓ **Q50** - **면책 문구**: "공식 판결문을 대신하지 않는 설명자료"라는 표시를 어떤 문구로 어디에 넣을까?

❓ **Q54** - **자동 점검 분류**: 기획은 "금액이나 인물 관계가 달라졌는지, 주장과 판단이 섞였는지, 설명이 필요한 용어가 있는지, 글과 그림의 의미가 맞는지"를 예로 든다. 분류를 어떻게 나눌까?

➡️ **"뜻이 달라졌을 수 있는 것"과 "더 쉽게 만들 수 있는 것"을 나눈다.**

| 묶음             | 분류           | 수준      | 예                                                          |
| ---------------- | -------------- | --------- | ----------------------------------------------------------- |
| 뜻이 달라졌나요  | 숫자·날짜      | 확인 필요 | 원문은 보증금 1억 원인데 문장은 1,000만 원                  |
|                  | 인물 관계      | 확인 필요 | 돈을 돌려줄 사람과 받을 사람이 뒤바뀜, 호칭이 섞임          |
|                  | 주장·판단 섞임 | 확인 필요 | "법원의 판단" 카드에 B씨의 주장이 들어감                    |
|                  | 글·그림 뜻     | 확인 필요 | "돌려주라고 결정했어요"라는 글에 "이미 돈을 받은 모습" 그림 |
|                  | 원문 근거 없음 | 확인 필요 | 근거가 연결되지 않은 문장                                   |
|                  | 구조 변경      | 확인 필요 | 초안을 만든 뒤 사건 구조가 바뀜(Q27)                        |
| 더 쉽게 읽히나요 | 어려운 말      | 살펴보기  | "임대차계약"에 풀이가 없음, 문장에 없는 풀이                |
|                  | 긴 문장        | 살펴보기  | 한 문장에 두 가지 내용                                      |
| 결과물 준비      | 대체텍스트     | 확인 필요 | 그림에 대체텍스트가 없음                                    |

목 서버는 fixture를 바탕으로 이 분류의 항목을 돌려준다. 제작자가 해당 부분을 고치면 다음 점검에서 사라지도록 아주 단순한 규칙으로 흉내 낸다(서버 연동 때 지움).

❓ **Q55** - **점검을 언제 실행할까**: 자동 점검은 비용이 드는 서버 호출이다. 언제 돌리고, "문제없음 확인"은 다시 점검할 때 어떻게 될까?

➡️

- [다시 점검]으로 언제든 직접 실행할 수 있다.
- "문제없음 확인"은 대상·분류·내용이 같은 항목이면 다시 점검해도 유지된다. 대상 문장이 바뀌면 새 항목으로 본다.
- 편집기의 문장 도구 패널은 마지막 점검 결과 중 그 문장의 항목을 보여 준다. 편집기에서는 자동 점검을 하지 않는다. 점검 뒤 바뀐 문장이면 "점검 뒤 바뀐 문장이에요"라고 표시한다.

❓ **Q56** - **"AI가 정확성을 보장하지 않는다"를 어떻게 표현할까**: 기획은 점검을 "제작자의 확인을 돕는 기능"으로 둔다고 했다.

➡️

- 항목이 0개일 때: "찾은 문제가 없어요. 그래도 체크리스트로 직접 확인해 주세요."
- "통과", "정확함", "일치함", 초록 체크 표시처럼 보증으로 읽히는 표현은 쓰지 않는다. 스크린샷의 "금액이 일치합니다 · 확인됨" 같은 표현을 쓰지 않는다.

❓ **Q58** - **PDF 저장 방식**: "PDF로 저장"을 무엇으로 할까?

❓ **Q60** - **"검토 완료"의 정의**: 무엇을 해야 검토가 끝난 것일까? 검토 뒤에 고치면?

➡️

- 조건: 남은 "확인 필요" 항목 0개(고쳐서 사라졌거나 문제없음 확인) + 최종 확인 체크리스트 전부 체크.
- 체크리스트(그림을 쓰지 않으면 3번은 빠짐):
  1. 금액, 날짜, 기간을 원문과 비교했어요.
  2. 누가 누구에게 무엇을 하는지 원문과 같아요.
  3. 그림이 글의 뜻과 맞아요.
  4. 당사자의 주장과 법원의 판단·결정이 섞이지 않았어요.
- [검토 마치기] 대화상자에 체크리스트와 함께 "살펴보기 M개, 대조하지 않은 문장 K개가 남았어요"를 보여 준다. 이 둘은 막지 않는다.
- 완료하면 그때의 문서 수정 번호와 함께 "검토 완료"를 기록한다. 그 뒤 문서가 바뀌면 "검토 후 수정됨"이 되고, 다시 마치려면 체크리스트를 새로 체크해야 한다. 검토 완료는 특정 수정 번호에 대한 확인이기 때문이다.

---

## Round 8: 내보내기 조건과 게시본

> Round 7 확정 답(검토 작업 큐, 검토 완료의 정의와 무효화)을 전제로 한다.

❓ **Q61** - **내보내기 조건**: 기획은 "검토한 버전을 PDF로 저장하거나 읽기 화면으로 제공"한다고 한다. 검토를 마치지 않았으면 내보내기를 막을까?

➡️ **PDF와 읽기 화면 공개의 조건을 다르게 둔다.**

- **PDF 저장은 알리고 허용한다.** 검토 완료가 아니면 "아직 검토를 마치지 않았어요(확인 필요 2개)" 대화상자에서 [검토하러 가기] / [검토 전 초안으로 저장]을 고른다. 검토 전 PDF는 모든 쪽에 "검토 전 초안 · 배포하지 마세요" 띠가 찍힌다. 동료에게 보여 줄 초안 PDF는 필요하지만, 최종본처럼 보여서는 안 된다.
- **읽기 화면 공개는 막는다.** 검토 완료 상태에서만 켤 수 있다. 링크는 독자에게 곧바로 가는 통로라서, 검토하지 않은 설명이 독자에게 닿으면 안 된다.

---

❓ **Q62** - **게시본(버전) 모델**: 내보낸 결과물과 계속 편집하는 문서의 관계는?

➡️

- 내보낼 때마다 그 순간 문서의 **게시본(스냅샷)**을 만든다: 번호(v1, v2…), 만든 시각, 그때의 검토 상태, 문서 수정 번호.
- PDF와 읽기 화면은 모두 게시본에서 만든다. 게시한 뒤에 편집해도 이미 내보낸 결과물은 바뀌지 않는다.
- 같은 수정 번호로 다시 내보내면 새 게시본을 만들지 않고 기존 것을 쓴다.
- ⑥ 화면에 게시본 이력(번호, 시각, 검토 상태, [PDF 다시 저장], 공개 중 표시)을 보여 준다.
- 현재 문서가 최신 게시본 이후에 바뀌었으면 "게시본 이후 수정됨"을 표시한다.
- 게시본끼리 비교, 삭제, 되살리기는 범위 밖이다.

---

## Round 9: 읽기 화면 공개

> Round 8 확정 답(PDF는 알리고 허용하고 공개는 막음, 게시본 스냅샷)을 전제로 한다.

❓ **Q63** - **읽기 화면 링크 공개**: 링크 제공을 어떻게 다룰까?

➡️

- [읽기 화면 공개] 스위치: 켜면 검토 완료된 현재 문서로 게시본을 만들고(같은 수정 번호의 게시본이 있으면 그것을 쓰고) 공개 게시본으로 정한다. 끄면 독자 화면이 "지금은 볼 수 없는 자료예요"로 바뀐다.
- 공개 중이면 주소, [주소 복사], [새 탭에서 열기], "v3 · 9월 13일 공개"를 보여 준다.
- 공개 게시본보다 새로운 검토 완료 문서가 있으면 [새 버전으로 바꾸기]를 보여 준다.
- 주소는 `/read/[projectId]`로 고정한다. 공개 게시본이 바뀌어도 독자에게 준 주소는 그대로다.
- QR 코드는 범위 밖이다.

---

## Round 10: 마무리

> 앞 라운드의 확정 답을 모두 전제로 한다. 남은 frontier는 작업함 세부, 범위 밖 확인, 구현 순서다.

❓ **Q64** - **작업함**: 작업함에서 무엇을 보여 주고 무엇을 할 수 있을까?

➡️

- 최근 수정 순 목록. 행마다 제목, 사건번호, 지금 단계, 검토 상태, 공개 여부, 마지막 수정 시각.
- 행을 누르면 진행한 가장 먼 단계로 이어서 한다. 행 메뉴에 [삭제](확인 대화상자).
- 상단에 [새 자료 만들기]. 빈 상태는 "아직 만든 자료가 없어요" + [새 자료 만들기] + [샘플로 체험하기].
- 맨 아래에 작은 [데모 데이터 초기화](확인 대화상자).
- 검색, 정렬 선택, 폴더는 범위 밖이다.

---

❓ **Q65** - **범위 밖 최종 확인**: 이번에 만들지 않는 것을 한곳에 모으면?

➡️

- 서버 쪽 전부: 실제 AI, 실제 API·엔드포인트, 인증과 권한, 실제 PDF 파일 생성, PDF 텍스트 추출.
- 협업: 공유 문서, 댓글, 동시 편집.
- 스크린샷에만 있던 화면: 용어 사전 페이지, 설정 페이지, 카드뉴스 export, 도움말.
- PDF 원본 보기, 스캔 PDF·OCR, HWP 입력.
- 편집: 끌어다 놓기, 구획 추가·순서 변경, 원문 검색, 게시본 비교·되살리기.
- 독자 화면: 읽어 주기(TTS), QR 코드, 다국어.
- 1024px 미만 화면에서 제작하기.
- 분석 도구·로그 수집, E2E 테스트, 컴포넌트 단위 테스트.

---

❓ **Q66** - **구현 순서(짧은 단위)**: 어떤 순서로 잘라서 구현할까?

➡️ **기반 → 목 데이터 → 화면 순서로, 한 단위가 커밋 하나다.** 도메인 연산이 들어가는 단위는 테스트를 먼저 쓴다.

1. 개발 기반: 의존성, Vitest·typecheck 스크립트, providers(QueryClient, Toaster), 종이 면 토큰
2. 도메인 스키마(zod)와 단계 계산(테스트)
3. 가상 판결문 fixture(원문·구조·초안)와 목 그림 에셋
4. ApiClient 인터페이스와 목 어댑터(IndexedDB 저장, 지연, 실패 흉내)
5. 작업함 화면
6. ① 새 자료 화면, 멀티스텝 로더, 분석 흐름
7. 프로젝트 셸(상단 바, 단계 표시, 들어갈 수 없는 단계 안내, 제목 편집)
8. 원문 뷰어(구획 이동, 근거 강조, 드래그 선택)
9. ② 구조 도메인 연산(옮기기·근거·초안 조건, 테스트)과 구조 편집 스토어
10. ② 사건 구조 확인 화면과 초안 만들기
11. ③ 문서 도메인 연산(문장·카드 편집, 대조, 되돌리기, 테스트)과 편집 스토어, 자동 저장
12. 자료 렌더러(편집 모드), 3단 편집기, 선택과 원문 연결
13. ③ 직접 수정, 문장·카드 편집, 대조 표시, 되돌리기 UI
14. ③ 어절 차이 계산(테스트)과 더 쉽게 바꾸기·문장 나누기
15. ③ 용어 설명 추가
16. ③ 그림 바꾸기와 올리기
17. ③ 근거 편집, 구조 변경 배너와 초안 다시 만들기
18. ④ 점검 목과 검토 화면(목록·상세·동작)
19. ④ 검토 마치기(체크리스트, 완료 기록, 무효화)
20. 자료 렌더러 읽기 모드와 독자 화면(`/read`)
21. 쪽 나누기(테스트), 인쇄 레이아웃, `/print`
22. ⑤ 미리보기(읽기·인쇄 탭)
23. ⑥ 내보내기(게시본, PDF 저장, 공개 스위치, 이력)
24. 마무리: 404·오류 화면, 접근성 점검, 코드 리뷰 반영

## Round 11: 스펙을 쓰다가 드러난 가지

> Round 10에서 frontier가 비었다고 보고 스펙을 쓰기 시작했다. 데이터 흐름을 문장으로 옮기다 보니 아직 방문하지 않은 가지 세 개가 드러나서 이 라운드로 더한다.

❓ **Q67** - **"문서 수정 번호"의 기준**: 검토 완료와 게시본은 문서 수정 번호에 묶인다(Q24, Q60, Q62). 그런데 대조 표시나 근거 변경처럼 독자에게 보이지 않는 변경도 자동 저장된다. 이런 변경도 수정 번호를 올려서 "검토 후 수정됨"을 만들어야 할까?

➡️ **번호를 둘로 나눈다.**

- **저장 번호**: 저장할 때마다 오른다. 자동 저장 순서를 맞추는 데만 쓴다.
- **내용 번호**: 독자에게 보이는 내용(문서 제목, 구획 제목, 카드와 카드 역할, 문장 텍스트, 그림과 대체텍스트, 용어 풀이)이 바뀔 때만 오른다. 검토 완료, 게시본, "검토 후 수정됨", "게시본 이후 수정됨"은 모두 내용 번호를 기준으로 한다.
- 대조 표시와 근거 변경은 검토를 무효화하지 않는다.
- 독자에게 보이는 내용만 뽑는 함수를 도메인 모듈에 둔다. 게시본에는 이 결과만 저장해서 근거나 대조 표시 같은 제작용 정보가 독자 쪽으로 새지 않게 한다.
- 사건 구조도 같은 원칙이다. AI "확인 필요" 표시를 끄는 것은 구조 수정 번호를 올리지 않는다(초안보다 구조가 새롭다는 표시가 괜히 뜨지 않게).

---

❓ **Q68** - **분석을 취소하거나 실패하면 자료가 남을까**: ①에서 분석 도중 취소하거나 실패했을 때 작업함에 반쯤 만든 자료가 남아야 할까?

➡️ **남기지 않는다.** "자료 만들기"는 올리기와 분석을 합친 요청 하나로 보고, 분석이 끝나야 자료가 생긴다. 그래서 작업함에는 분석이 끝난 자료만 있고, ②는 언제나 들어갈 수 있다. 서버가 비동기 작업 방식이 되면 그때 "분석 중" 상태를 더한다.

---

❓ **Q69** - **가상 판결문의 표기**: 샘플 판결문에 실제 법원 이름과 그럴듯한 사건번호를 쓸까?

➡️ **가상의 법원 이름("가온지방법원")을 쓰고, 원문 맨 위에 "[데모용 가상 판결문]"이라고 적는다.** 실제 법원·사건과 헷갈리지 않게 하려는 것이다. 인물은 판결문 관행대로 원고 A, 피고 B로 적는다. 샘플 초안에는 점검 기능을 시연하려고 일부러 넣은 문제를 둔다: 틀린 금액, 법원 판단 카드에 섞인 주장, 원문 근거가 없는 문장, 풀이 없는 법률 용어, 결정 내용과 뜻이 어긋난 그림, 대체텍스트가 없는 그림, 긴 문장.

---

## 종료

frontier가 비었다. 설계 트리의 모든 가지(범위·사용자, 목 API·데이터·저장소, URL·단계 규칙, 기기·셸·테마, 원문 단위, 사건 구조, 문서 모델, ② 화면, ③ 편집기 전체, ④ 검토, ⑤ 미리보기·독자 화면·인쇄, ⑥ 내보내기·게시본·공개, 작업함, 오류·접근성·성능, 범위 밖, 구현 순서, 수정 번호 기준, 자료 생성 시점, 샘플 표기)를 방문했다. 사용자 위임에 따라 모든 추천안을 확정 답으로 채택하고 스펙 작성으로 넘어간다.
