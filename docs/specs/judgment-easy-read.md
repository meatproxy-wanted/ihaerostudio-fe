# 스펙: 판결문 쉬운 설명자료 제작 흐름

## Problem Statement

판결문을 발달장애가 있는 성인이 이해할 수 있는 쉬운 설명자료(쉬운 글과 그림)로 만드는 제작자는, 범용 LLM으로 초안을 금방 얻을 수 있다. 문제는 그다음이다.

- AI 초안의 문장이 원문 어디에서 왔는지 알 수 없어서, 제작자가 판결문 전체를 다시 뒤지며 한 문장씩 대조해야 한다.
- AI는 당사자가 **주장한 내용**과 법원이 **인정하거나 결정한 내용**을 자주 섞는다. 금액이 바뀌거나, 누가 누구에게 돈을 줘야 하는지가 뒤집히기도 한다. 이런 오류는 독자에게 해로운 오해를 남긴다.
- 문장을 더 쉽게 고치거나 나누는 작업, 어려운 말 풀이, 글에 맞는 그림 고르기가 여러 도구에 흩어져 있다. AI에게 다시 고쳐 달라고 하면 결과가 통째로 바뀌어 무엇이 달라졌는지 알기 어렵다.
- 글과 그림의 뜻이 어긋나는 경우(예: "법원이 돈을 주라고 결정했다"는 글에 "이미 돈을 받은 모습" 그림)를 체계적으로 확인할 방법이 없다.
- 최종 결과물을 독자가 읽기 좋은 화면과 인쇄물로 만들고, "공식 판결문을 대신하지 않는다"는 안내를 빠짐없이 넣는 일도 손으로 해야 한다.

즉, 초안을 **원문과 대조하고, 고치고, 검토하고, 내보내는** 과정이 한곳에 없다.

## Solution

"이해로 스튜디오"는 쉬운 글을 더 잘 써 주는 도구가 아니라, AI 초안을 **원문과 비교해 최종 자료로 완성하는 과정**을 한곳에서 돕는 제작 도구다. 여섯 단계로 흐른다.

1. **판결문 올리기**: PDF를 올리거나 텍스트를 붙여 넣고, 문체·인물 호칭·그림 사용 세 가지만 예시를 보며 고른다.
2. **사건 구조 확인**: AI가 정리한 사건 정보, 등장인물, 핵심 사실(금액·날짜), 당사자별 주장, 법원의 판단, 최종 결정을 원문과 나란히 보며 고친다. 주장과 법원의 판단·결정은 서로 다른 목록이라 섞였으면 항목을 옮겨서 고친다. 원문과 비교했음을 확인한 뒤 초안을 만든다.
3. **쉬운 글·그림 편집**(핵심 화면): 왼쪽 원문, 가운데 독자 화면과 같은 모양의 쉬운 자료, 오른쪽 문장 도구. 문장을 누르면 원문 근거가 강조된다. 직접 수정, 더 쉽게 바꾸기, 문장 나누기, 용어 설명 추가, 그림 바꾸기를 할 수 있고, AI 수정안은 전후 차이를 본 뒤에만 적용된다. 문장마다 원문 대조 여부를 표시해 진행률로 보여 준다.
4. **검토하기**: 자동 점검이 금액·인물 관계·주장과 판단의 섞임·글과 그림의 뜻·근거 없는 문장·어려운 말 등을 "확인할 항목"으로 보여 준다. 정확성을 보장하는 기능이 아니라 확인을 돕는 기능임을 분명히 밝히고, 제작자가 체크리스트로 직접 확인해 검토를 마친다.
5. **결과물 미리보기**: 독자 화면을 기기 폭별로, 인쇄물을 실제 A4 쪽 단위로 확인한다.
6. **내보내기**: 게시본을 만들어 PDF로 저장하거나(검토 전이면 모든 쪽에 초안 표시) 검토를 마친 게시본만 독자용 읽기 화면으로 공개한다. 모든 결과물에 "공식 판결문을 대신하지 않는 설명자료"라는 안내가 자동으로 들어간다.

독자는 링크로 받은 읽기 화면에서 **누가 나오는지 → 무엇을 결정했는지 → 왜 그렇게 결정했는지 → 어려운 말 풀이** 순서로, 한 구획씩 큰 글씨와 그림으로 읽는다.

이번 구현은 프론트엔드만 다룬다. AI와 API는 별도 서버 프로젝트가 만들며, 이 저장소는 서버가 있다고 가정한 목 API로 동작한다. 데모 모드에서는 어떤 판결문을 넣어도 준비된 가상 판결문 사건으로 분석된다.

## User Stories

### 작업함

1. 제작자로서, 내가 만든 자료를 최근 수정 순으로 보고 싶다. 그래야 하던 작업을 바로 찾을 수 있다.
2. 제작자로서, 자료마다 사건번호, 지금 단계, 검토 상태, 공개 여부, 마지막 수정 시각을 보고 싶다. 그래야 어떤 자료에 손이 더 필요한지 안다.
3. 제작자로서, 자료를 누르면 진행한 가장 먼 단계로 이어서 하고 싶다. 그래야 단계를 다시 찾아가지 않는다.
4. 제작자로서, 필요 없는 자료를 확인 과정을 거쳐 지우고 싶다. 그래야 실수로 지우지 않는다.
5. 제작자로서, 자료가 하나도 없을 때 새 자료 만들기와 샘플 체험 중 하나를 바로 고르고 싶다.
6. 시연하는 사람으로서, 데모 데이터를 초기화하고 싶다. 그래야 시연을 처음부터 다시 할 수 있다.

### ① 판결문 올리기

7. 제작자로서, 판결문 PDF를 끌어다 놓거나 파일 선택으로 올리고 싶다.
8. 제작자로서, PDF가 없을 때 판결문 텍스트를 붙여 넣고 싶다.
9. 제작자로서, PDF가 아니거나 20MB를 넘는 파일, 100자보다 짧은 텍스트를 넣으면 이유를 바로 알고 싶다.
10. 제작자로서, 올린 파일의 이름과 크기를 보고 빼고 싶다.
11. 제작자로서, 문체(해요체/합니다체)를 예시 문장을 보며 고르고 싶다. 그래야 결과물이 어떤 말투일지 미리 안다.
12. 제작자로서, 인물 호칭 방식(A씨·B씨 / 하는 일로 / 원고·피고와 쉬운 설명)을 예시를 보며 고르고 싶다.
13. 제작자로서, 그림을 쓸지 말지 고르고 싶다.
14. 시연하는 사람으로서, 샘플 판결문으로 곧바로 시작하고 싶다.
15. 제작자로서, 지금이 데모 모드라서 어떤 판결문을 넣어도 샘플 사건으로 분석된다는 것을 알고 싶다. 그래야 결과를 실제 분석으로 오해하지 않는다.
16. 제작자로서, 분석하는 동안 지금 무엇을 하는지 단계별로 보고 싶다. 그래야 기다리는 동안 불안하지 않다.
17. 제작자로서, 분석을 취소하고 입력한 내용이 남은 화면으로 돌아가고 싶다.
18. 제작자로서, 분석이 실패하면 이유와 다시 시도 버튼을 보고 싶다.
19. 제작자로서, 분석이 끝나야 작업함에 자료가 생기길 원한다. 그래야 반쯤 만든 자료가 쌓이지 않는다.

### 프로젝트 공통 틀

20. 제작자로서, 어느 단계에서든 여섯 단계와 지금 위치를 한 줄로 보고 싶다.
21. 제작자로서, 필요한 데이터가 있는 단계라면 순서와 상관없이 오가고 싶다.
22. 제작자로서, 단계마다 완료, 검토 후 수정됨 같은 상태를 보고 싶다.
23. 제작자로서, 아직 들어갈 수 없는 단계에 들어가면 무엇을 먼저 해야 하는지 안내받고 싶다.
24. 제작자로서, 자료 제목을 상단에서 바로 고치고 싶다.
25. 제작자로서, 저장 상태(저장 중 / 저장됨 / 저장 못 함)를 늘 보고 싶다.
26. 제작자로서, 로고를 눌러 작업함으로 돌아가고 싶다.
27. 제작자로서, 화면이 너무 좁으면 넓은 화면에서 편집하라는 안내를 받고 싶다.

### ② 사건 구조 확인

28. 제작자로서, AI가 정리한 사건 정보(사건명, 사건번호, 법원, 선고일)를 원문과 나란히 보며 고치고 싶다.
29. 제작자로서, 등장인물의 원문 표기, 법적 지위, 호칭, 쉬운 역할 설명을 확인하고 고치고 싶다.
30. 제작자로서, 인물마다 호칭을 따로 바꾸고 싶다.
31. 제작자로서, 금액·날짜·기간 같은 핵심 사실을 따로 모아 보고 고치고 싶다. 그래야 뒤에서 숫자를 대조할 기준이 생긴다.
32. 제작자로서, 당사자가 주장한 내용과 법원이 판단·결정한 내용을 서로 다른 영역에서 보고 싶다. 그래야 둘이 섞였는지 한눈에 안다.
33. 제작자로서, 주장이 법원의 판단이 아니라는 안내를 영역 머리에서 보고 싶다.
34. 제작자로서, 잘못 분류된 항목을 주장, 법원의 판단, 최종 결정 사이로 옮기고 싶다. 옮겨도 근거는 남아 있기를 원한다.
35. 제작자로서, 주장이 누구의 주장인지 바꾸고 싶다.
36. 제작자로서, 법원의 판단이 어느 주장을 다루고, 그 주장을 받아들였는지 표시하고 싶다.
37. 제작자로서, 항목을 선택하면 원문의 근거 부분으로 원문이 스크롤되고 강조되길 원한다.
38. 제작자로서, 틀린 근거를 빼고, 원문을 드래그해 새 근거를 연결하고 싶다.
39. 제작자로서, AI가 확인이 필요하다고 표시한 항목과 그 이유를 보고 싶다.
40. 제작자로서, 확인이 끝난 AI 표시를 끄고 싶다. 내용을 고치면 표시가 저절로 사라지길 원한다.
41. 제작자로서, 인물, 핵심 사실, 주장, 판단, 결정을 추가하거나 지우고 싶다.
42. 제작자로서, 화면을 나갔다 와도 고친 내용이 남아 있길 원한다.
43. 제작자로서, 초안을 만들 수 없는 이유(인물 없음, 결정 없음, 인물 없는 주장, 빈 문구, 확인 체크 안 함)를 보고 싶다.
44. 제작자로서, "원문과 비교해 확인했어요"를 체크한 뒤에 초안을 만들고 싶다. 그래야 비교를 건너뛰지 않는다.
45. 제작자로서, AI 확인 표시가 남아 있으면 초안을 만들기 전에 한 번 더 안내받고 싶다.
46. 제작자로서, 초안을 만드는 동안 단계별 진행 상황을 보고 취소할 수도 있길 원한다.
47. 제작자로서, 문체·호칭·그림 설정을 ②에서 다시 바꾸고 싶다.
48. 제작자로서, 초안이 있는데 구조나 설정을 바꿨을 때 초안이 자동으로 덮어써지지 않길 원한다.
49. 제작자로서, 구조가 바뀐 뒤 초안을 다시 만들면 무엇이 사라지는지 알고 고르고 싶다.

### ③ 쉬운 글·그림 편집

50. 제작자로서, 원문, 쉬운 자료, 문장 도구를 한 화면의 세 칸에서 보고 싶다.
51. 제작자로서, 칸 크기를 조절하고 원문 칸을 접고 싶다. 그리고 그 크기가 기억되길 원한다.
52. 제작자로서, 쉬운 자료를 독자가 보는 모양(카드, 그림, 한 줄에 한 문장) 그대로 보며 편집하고 싶다.
53. 제작자로서, 원문의 구획(주문, 청구취지, 이유의 소제목)으로 바로 이동하고 싶다.
54. 제작자로서, 문장을 누르면 원문 칸이 그 문장의 근거로 따라가 강조되길 원한다.
55. 제작자로서, 근거가 여러 개면 차례로 오가고 싶다.
56. 제작자로서, 원문의 강조 부분을 누르면 그것을 근거로 쓰는 문장이 선택되길 원한다.
57. 제작자로서, 원문 근거가 없는 문장을 한눈에 알아보고 싶다.
58. 제작자로서, 키보드만으로 문장을 오가고, 수정을 시작하고, 선택을 풀고 싶다.
59. 제작자로서, 선택한 문장의 원문 근거 인용과 그 문장의 점검 항목을 도구 칸에서 함께 보고 싶다.
60. 제작자로서, 아무것도 선택하지 않았을 때 문서 요약(진행 상황, 근거 없는 문장, 점검 결과, 용어)을 보고 싶다.
61. 제작자로서, 문장을 제자리에서 직접 고치고, Enter로 적용하고 Esc로 취소하고 싶다.
62. 제작자로서, 문장을 아래에 추가하고, 지우고, 같은 카드 안에서 옮기고 싶다.
63. 제작자로서, 구획에 맞는 역할의 카드를 추가하고, 확인을 거쳐 지우고, 같은 구획 안에서 옮기고 싶다.
64. 제작자로서, 문서 제목과 구획 제목을 제자리에서 고치고 싶다.
65. 제작자로서, 문장마다 원문과 대조했는지 표시하고 전체 대조 진행률을 보고 싶다.
66. 제작자로서, 단축키 한 번으로 대조 완료를 표시하고 다음 문장으로 넘어가고 싶다. 그래야 문서 전체를 빠르게 훑는다.
67. 제작자로서, 내가 직접 고친 문장은 대조한 것으로 처리되길 원한다.
68. 제작자로서, 선택한 문장을 더 쉽게 바꾼 수정안을 최대 세 개 받아 보고 싶다.
69. 제작자로서, 수정안의 전후 차이를 어절 단위 강조로 보고 싶다.
70. 제작자로서, 수정안에서 숫자가 바뀌면 강하게 경고받고 싶다. 그래야 금액이 몰래 바뀌지 않는다.
71. 제작자로서, 수정안을 그대로 적용하거나, 고쳐서 적용하거나, 다시 받거나, 닫고 싶다.

## Implementation Decisions

### 경계와 층

- **서버 코드를 만들지 않는다.** Route Handler, 서버 액션으로 흉내 낸 API, AI SDK 호출, 서버 쪽 PDF 처리를 이 저장소에 두지 않는다.
- 층은 다음과 같다: 화면(App Router 경로) → 기능 컴포넌트 → 상태(서버 상태 캐시 / 화면별 편집 스토어) → **API 클라이언트 인터페이스** → 목 어댑터. 모든 층이 **도메인 모듈**(스키마와 순수 연산)을 공유한다.
- 화면과 상태 층은 API 클라이언트 인터페이스만 안다. 목 어댑터, fixture, 목 규칙, 목 그림은 한 모듈에 격리하고 "서버 연동 때 삭제"를 표시한다. 서버가 준비되면 같은 인터페이스를 HTTP로 구현한 어댑터로 바꾼다. 엔드포인트와 HTTP 모양은 그때 정한다.
- API 클라이언트는 응답을 도메인 스키마로 파싱한 뒤 넘긴다(목 어댑터도 같은 경계를 지난다). 실패는 사용자에게 보여 줄 메시지를 가진 공통 오류 형태로 바꾼다. 오래 걸리는 요청(분석, 초안 생성, 점검)은 중단 신호를 받는다.

### 주소와 레이아웃

| 주소                              | 화면                   | 비고                                         |
| --------------------------------- | ---------------------- | -------------------------------------------- |
| `/`                               | 작업함                 |                                              |
| `/new`                            | ① 새 자료 만들기       | `?sample=1`이면 샘플 텍스트를 채움           |
| `/projects/[projectId]`           | 이어서 할 단계로 이동  |                                              |
| `/projects/[projectId]/structure` | ② 사건 구조 확인       |                                              |
| `/projects/[projectId]/edit`      | ③ 편집기               | 선택한 문장·카드와 열린 도구를 쿼리로 딥링크 |
| `/projects/[projectId]/review`    | ④ 검토하기             | 선택한 항목·필터를 쿼리로 유지               |
| `/projects/[projectId]/preview`   | ⑤ 미리보기             | 탭·기기 폭을 쿼리로 유지                     |
| `/projects/[projectId]/export`    | ⑥ 내보내기             |                                              |
| `/read/[projectId]`               | 독자용 읽기 화면       | 공개 게시본만                                |
| `/print/[projectId]`              | 인쇄 전용 화면         | 게시본 번호를 쿼리로 받음                    |
| `/showcase`                       | 기존 컴포넌트 쇼케이스 | 유지                                         |

- 프로젝트 경로들은 상단 바(로고, 제목, 단계 표시, 저장 상태, 다음 단계 버튼)를 공유하는 레이아웃을 쓴다. 전역 사이드바는 없다.
- 독자·인쇄 화면은 앱 틀과 테마 설정이 없는 별도 route group 레이아웃이다. 루트 레이아웃은 새로 만들지 않는다(루트 레이아웃이 다르면 이동할 때 전체 새로고침이 일어난다).
- Next.js 16 규칙을 따른다. `params`와 `searchParams`는 Promise라서 서버 컴포넌트는 `await`, 클라이언트 컴포넌트는 `use()`로 읽는다. `useSearchParams`를 쓰는 컴포넌트는 Suspense 경계 안에 둔다. 브라우저 전용 코드(IndexedDB, 인쇄, 선택 영역)는 렌더 중에 실행하지 않는다.
- 제작 화면은 1280px 이상에 최적화하고, 1024~1279px에서는 원문 칸을 접어 쓰며, 1024px 미만에서는 안내 화면을 보여 준다. 독자 화면은 모바일 우선이다.

### 도메인 모델

도메인 타입의 원천은 zod 스키마다. 날짜·시각은 ISO 문자열이다.

**프로젝트(요약)**: 작업함과 단계 표시에 필요한 정보만 담는다.

- ID, 제목, 만든·고친 시각
- 설정(문체: 해요체·합니다체 / 호칭: A씨·B씨, 하는 일, 원고·피고와 설명 / 그림: 함께·글만)과 설정 수정 번호
- 원문 정보(PDF·텍스트, 파일 이름, 크기, 글자 수), 사건번호
- 구조 수정 번호
- 문서 정보(없을 수 있음): 저장 번호, 내용 번호, 초안이 기준으로 삼은 구조 수정 번호와 설정 수정 번호, 문장 수, 대조한 문장 수
- 검토 정보: 마지막 점검 때의 내용 번호, 남은 확인 필요 수, 검토 완료한 내용 번호와 시각
- 내보내기 정보: 최신 게시본 번호와 그 내용 번호, 공개 게시본 ID

**원문**: 순서 있는 문단 목록. 문단마다 ID, 구획(머리 / 주문 / 청구취지 / 이유), 이유의 소제목, 쪽 번호(PDF일 때), 텍스트.

**근거**: 문단 ID + 시작·끝 글자 위치. 문장과 구조 항목은 근거를 여러 개 가질 수 있다.

**AI 확인 표시**: 코드, 이유 문구. 구조 항목에 붙는다.

**사건 구조**:

- 사건 정보: 사건명, 사건번호, 법원, 선고일
- 등장인물: ID, 원문 표기, 법적 지위, 호칭, 쉬운 역할 설명, 근거, 확인 표시
- 핵심 사실: ID, 종류(금액·날짜·기간·기타), 이름, 값, 근거, 확인 표시
- 주장: ID, 인물 ID, 내용, 근거, 확인 표시
- 법원의 판단: ID, 내용, 다루는 주장 ID 목록, 받아들임 여부(받아들임·받아들이지 않음·일부·해당 없음), 근거, 확인 표시
- 최종 결정: ID, 내용, 근거, 확인 표시
- 수정 번호. 확인 표시를 끄는 변경은 수정 번호를 올리지 않는다.

주장·판단·결정은 서로 다른 목록이다. 섞임을 고치는 방법은 항목을 다른 목록으로 옮기는 것이다.

**쉬운 설명자료 문서**:

- 제목, 저장 번호, 내용 번호, 기준 구조 수정 번호, 기준 설정 수정 번호
- 구획 네 개(고정 순서): 누가 나오나요 / 무엇을 결정했나요 / 왜 그렇게 결정했나요 / 어려운 말 풀이. 구획마다 제목을 가진다. 앞 세 구획은 카드 목록을 가진다.
- 카드: ID, 역할(인물 소개·배경·주장·법원의 판단·최종 결정), 인물 ID(인물 소개와 주장일 때), 그림 ID(없을 수 있음), 문장 목록(1개 이상)
- 문장: ID, 텍스트, 근거 목록, 출처(AI 초안·AI 수정안·직접 작성), 대조 여부
- 용어 풀이: ID, 용어, 쉬운 설명. 문장 속 위치는 저장하지 않고 화면에 그릴 때 글자 일치로 찾는다. 풀이 구획의 순서는 문서에 처음 나오는 순서다.
- 그림: ID, 주소, 대체텍스트, 의미 설명, 출처(그림 목록·직접 올림)

**독자용 내용**: 문서에서 독자에게 보이는 부분만 뽑은 것(제목, 구획 제목, 카드 역할과 라벨에 필요한 인물 호칭, 문장 텍스트, 그림 주소와 대체텍스트, 용어 풀이, 문체, 사건 정보). 근거, 대조, 출처는 뺀다. **내용 번호는 이 독자용 내용이 바뀔 때만 오른다.**

**점검 실행 결과**: 점검한 내용 번호, 실행 시각, 항목 목록. 항목은 안정 키(분류·대상·대상 내용으로 만듦), 묶음, 분류(숫자·날짜 / 인물 관계 / 주장·판단 섞임 / 글·그림 뜻 / 원문 근거 없음 / 구조 변경 / 어려운 말 / 긴 문장 / 대체텍스트), 수준(확인 필요·살펴보기), 제목, 설명, 대상(문장·카드·그림·용어·문서), 비교 근거(쉬운 문장, 원문 근거, 구조 값, 그림), 제안 수정안(문장 교체 텍스트, 없을 수 있음), 처리 상태(남음·문제없음 확인과 메모)를 가진다. "문제없음 확인"은 안정 키로 기억해서 다시 점검해도 유지한다.

**검토 완료 기록**: 내용 번호, 시각, 체크한 체크리스트 항목.

**게시본**: ID, 번호(v1, v2…), 만든 시각, 내용 번호, 그때의 검토 상태(검토 완료·검토 전), 독자용 내용 스냅샷.

### 도메인 연산 (테스트 seam)

React와 무관한 순수 함수로 두고 Vitest로 테스트한다. 스토어와 목 어댑터는 이 함수들을 호출만 한다.

- **단계 계산**: 프로젝트 요약으로 단계별 진입 가능 여부와 상태(완료·진행 전·주의 필요·검토 후 수정됨)를 계산한다. 이어서 할 단계도 계산한다. 초안이 없으면 ②, 점검한 적이 없으면 ③, 검토를 마치지 않았거나 검토 후 수정됐으면 ④, 그 밖에는 ⑥이다.
- **초안 만들기 조건**: 구조와 확인 체크로 막는 문제 목록(대상 항목 ID, 메시지)과 알릴 사항(남은 AI 확인 표시 수)을 돌려준다.
- **구조 연산**: 항목 추가·수정·삭제, 목록 사이 옮기기(주장으로 옮길 때 인물 지정, 근거 유지), 근거 추가·빼기, 확인 표시 끄기, 수정 번호를 올릴 변경인지 판단.
- **문서 연산**: 문장 수정·추가·삭제·이동, 카드 추가·삭제·이동, 수정안 적용(출처는 AI 수정안, 대조 해제, 근거 유지), 문장 나누기 적용(근거 복사), 직접 수정(출처는 직접 작성, 대조 완료), 대조 표시, 근거 추가·빼기, 용어 추가·수정·삭제, 그림 바꾸기·빼기와 대체텍스트 수정, 제목 수정, 초안 다시 만들 때 사라질 손본 문장 수 세기.
- **용어 등장**: 문장 텍스트에서 등록 용어의 위치를 찾고, 풀이 순서(처음 나온 순서)와 문서에 없는 용어를 계산한다.
- **되돌리기 이력**: 최대 50단계의 과거·미래 스택. 새 변경은 미래를 비운다.
- **어절 차이**: 두 문장을 어절(띄어쓰기 기준, 문장부호 분리)로 나눠 LCS로 같음·지움·넣음 조각을 돌려준다.
- **숫자 변경 감지**: 두 텍스트의 숫자 표현(금액, 날짜, 기간)을 뽑아 달라진 목록을 돌려준다. "1억 원"과 "100,000,000원"처럼 같은 금액의 다른 표기는 같다고 본다.
- **독자용 내용 뽑기**와 두 문서의 독자용 내용이 같은지 판단.
- **읽기 순서**: 독자용 내용으로 표지 → 구획 1~4 → 마침의 쪽 목록을 만든다.
- **쪽 채우기**: 블록(표지, 구획 제목, 카드, 용어 표 행)의 높이 목록과 본문 높이로 A4 쪽 구성을 만든다. 구획은 새 쪽에서 시작하고, 카드는 쪼개지 않고, 한 쪽보다 큰 블록은 혼자 둔다.

### API 클라이언트 인터페이스 (기능 묶음)

엔드포인트가 아니라 화면이 필요로 하는 동작의 목록이다. 서버와 맞출 때 이름과 모양은 바뀔 수 있다.

- **작업함**: 프로젝트 목록, 프로젝트 삭제, 데모 데이터 초기화
- **자료 만들기**: 원문(PDF 파일 또는 텍스트)과 설정을 받아 올리기와 분석을 끝낸 프로젝트를 돌려준다(중단 가능). 분석이 끝나야 프로젝트가 생긴다.
- **프로젝트**: 조회, 제목 바꾸기, 설정 바꾸기
- **원문**: 조회
- **사건 구조**: 조회, 저장(저장 뒤의 구조와 프로젝트 요약을 돌려줌)
- **문서**: 초안 만들기(중단 가능, 기존 문서가 있으면 덮어씀), 조회, 저장(저장 뒤의 저장 번호·내용 번호와 프로젝트 요약을 돌려줌)
- **편집 도움**: 더 쉽게 바꾸기(수정안 최대 3개), 문장 나누기(문장 2~~3개), 용어 후보, 용어 설명 초안, 그림 후보(4~~6개), 그림 올리기
- **검토**: 점검 실행(중단 가능), 마지막 점검 결과 조회, 항목 문제없음 확인·취소, 검토 완료 기록
- **내보내기**: 게시본 만들기(같은 내용 번호면 기존 게시본 반환), 게시본 목록, 게시본 조회, 공개 게시본 지정·해제
- **독자**: 공개 게시본 조회(없거나 비공개면 "볼 수 없음")

### 목 어댑터

- 저장소는 IndexedDB(얇은 key-value 래퍼)이고, 쓸 수 없으면 메모리를 쓴다. 올린 PDF는 파일 이름과 크기만 저장한다. 직접 올린 그림은 Blob으로 저장한다.
- 지연 시간: 분석 약 6초, 초안 약 7초, 편집 도움 약 1초, 점검 약 2초, 일반 조회·저장 약 0.3초. 중단 신호를 받으면 즉시 중단한다.
- 실패 흉내: 주소에 `mockFail` 쿼리(분석, 초안, 저장, 편집 도움, 점검, 내보내기 중 하나 이상)를 붙이면 그 탭 세션 동안 해당 요청이 실패한다. 무작위 실패는 없다.
- **가상 판결문 fixture 1건**: 가상의 "가온지방법원" 임대차보증금 반환 사건. 원고 A(세입자), 피고 B(집주인). 원문 맨 위에 "[데모용 가상 판결문]"을 적는다. 어떤 입력이든 이 사건의 원문과 구조를 돌려준다.
- 초안 fixture에는 점검 시연용 문제를 일부러 넣는다: 틀린 금액, 법원 판단 카드에 섞인 주장, 원문 근거가 없는 문장, 풀이 없는 법률 용어, 결정 내용과 뜻이 어긋난 그림, 대체텍스트가 없는 그림, 긴 문장.
- 편집 도움과 점검은 fixture를 먼저 찾고, 없으면 목 전용의 아주 단순한 규칙으로 흉내 낸다. 예: 작은 쉬운 말 사전 치환, 쉼표 기준 나누기, 용어 사전 조회, 카드 역할에 맞는 그림 후보, 문서 내용을 보고 점검 항목 만들기(핵심 사실에 없는 금액, 판단 카드 속 "~라고 했어요" 문장, 근거 없는 문장, 대체텍스트 없는 그림, 긴 문장, 풀이 없는 사전 용어, 그림 의미 태그와 결정 문장의 충돌, 구조 수정 번호 차이). 제작자가 고치면 다음 점검에서 항목이 사라진다. 이 규칙은 제품 로직이 아니다.
- 목 그림: hugeicons 무료 아이콘(MIT)을 조합한 픽토그램 장면 SVG 20장 안팎. 개발용 생성 스크립트로 만들어 정적 파일로 두고, 그림마다 의미 설명과 기본 대체텍스트, 의미 태그를 붙인다. "이미 돈을 받은 모습"과 "돈을 돌려주라고 결정하는 모습"을 둘 다 포함한다.
- 내용 번호 계산은 도메인 모듈의 독자용 내용 비교를 쓴다.

### 상태 관리

- **TanStack Query v5**: 브라우저에서 QueryClient 하나를 재사용하는 클라이언트 providers를 루트 레이아웃에 둔다. 엔터티별 쿼리 키 팩토리를 쓴다. 기본값은 staleTime 30초, 조회 재시도 1번, 변경 재시도 없음, 창 포커스 때 다시 불러오기 끔. 개발 모드에서만 Devtools를 켠다. 저장이 성공하면 돌려받은 값으로 캐시를 바로 갱신한다.
- **zustand v5**: 전역 스토어를 만들지 않는다. ②와 ③ 화면이 열릴 때 프로젝트 전용 스토어를 만들어 Context로 내려 준다. 스토어는 쿼리 데이터로 한 번 초기화한 작업 사본, 선택, 열린 수정안, 되돌리기 이력, 저장 상태를 가진다. 변경은 도메인 연산에 맡긴다. 객체를 돌려주는 selector는 얕은 비교를 쓴다. 문장 컴포넌트는 자기 문장만 구독한다.
- **자동 저장**: 작업 사본이 바뀌고 1초 동안 추가 변경이 없으면 저장한다. 저장 중에 또 바뀌면 끝난 뒤 이어서 저장한다. 저장하지 않은 변경이 있으면 탭을 닫을 때 브라우저 경고를 띄운다. 실패하면 토스트와 [다시 시도]를 보여 준다.
- **되돌리기**: ③에서 문서 변경 단위(도구 적용, 직접 수정 확정, 문장·카드 추가·삭제·이동, 용어·그림 변경)마다 한 단계, 최대 50단계. ⌘Z / ⇧⌘Z와 상단 바 버튼. 새로고침하면 이력은 사라진다.
- **URL 쿼리**: 선택한 문장·카드, 열린 도구, 검토 필터와 선택 항목, 미리보기 탭과 기기 폭, "검토에서 왔음" 표시.
- **localStorage**: 편집기 칸 크기, 독자 화면 글자 크기.
- **React Hook Form은 쓰지 않는다.** ① 폼은 로컬 상태로, ② 구조 편집은 도메인 연산과 편집 스토어로 처리하고, 검증은 도메인 함수가 돌려준 문제 목록을 항목 옆에 보여 준다.

### 화면별 결정

**작업함**

- 최근 수정 순 목록. 행에 제목, 사건번호, 지금 단계, 검토 상태, 공개 여부, 마지막 수정 시각. 행을 누르면 이어서 할 단계로 간다. 행 메뉴에 확인 대화상자를 거치는 삭제.
- 빈 상태: 새 자료 만들기, 샘플로 체험하기. 맨 아래 확인을 거치는 데모 데이터 초기화.

**① 새 자료 만들기**

- 가운데 단일 컬럼. PDF 올리기 / 텍스트 붙여넣기 탭. 데모 모드 안내.
- 설정 세 가지는 예시 문장이 보이는 선택 카드로 보여 준다. 기본값은 해요체, A씨·B씨, 글과 그림 함께.
- 제목은 받지 않고 분석 결과의 사건명으로 붙인다.
- [샘플 판결문으로 체험하기]는 샘플 텍스트를 채우고 바로 분석을 시작한다.
- 분석하는 동안 전체 화면 멀티스텝 로더를 띄운다. 성공하면 ②로 이동하고, 취소하면 입력이 남은 채로 머물고, 실패하면 오류 상자와 [다시 시도]를 보여 준다.

**프로젝트 상단 바와 단계 표시**

- 로고, 제자리에서 고치는 제목, 단계 1~6(상태 표시), 저장 상태, 원문 대조 진행률(③), 되돌리기(③), 다음 단계 버튼.
- 단계 규칙: ②는 항상, ③~⑥은 문서가 있으면 들어갈 수 있다. ①은 만든 뒤에는 완료 표시만 하고, 누르면 올린 원문과 설정 요약을 보여 준다.
- 들어갈 수 없는 단계에 들어가면 앞 단계로 안내하는 빈 상태 화면을 보여 준다.

**② 사건 구조 확인**

- 왼쪽 원문 뷰어, 오른쪽 구조 편집의 2단 분할.
- 오른쪽 순서: 사건 정보 → 등장인물 → 핵심 사실 → 당사자가 주장한 내용(인물별 묶음) → 법원이 판단한 내용 → 법원의 최종 결정. 상단에 구획 바로가기, "확인 필요 N개", [자료 설정].
- 주장 영역과 법원 영역은 다른 면이다. 주장 영역은 인물 색 점, 말풍선 아이콘, "당사자가 주장한 내용이에요. 법원이 인정한 사실이 아니에요"라는 머리말을 쓴다. 법원 영역은 법원 아이콘과 "법원이 판단하고 결정한 내용이에요"라는 머리말을 쓴다.
- 항목: 제자리 편집, 추가·삭제, 목록 사이 옮기기, 인물 바꾸기, 판단이 다루는 주장과 받아들임 여부, 근거 목록(선택하면 원문 강조, 빼기, 원문 드래그로 추가), AI 확인 표시와 [확인했어요].
- 편집 스토어에 담고 자동 저장한다.
- 맨 아래에 막는 조건 목록, "원문과 비교해 확인했어요" 체크박스(화면에 들어올 때마다 해제 상태), [초안 만들기]. AI 확인 표시가 남아 있으면 확인 대화상자를 띄운다. 초안이 이미 있으면 [초안 다시 만들기]로 바뀌고, 사라질 손본 문장 수를 대화상자에 보여 준다.
- 초안이 있는 상태로 들어오면 "고친 내용은 초안을 다시 만들어야 반영돼요"라고 안내한다.

**③ 편집기**

- 크기 조절 가능한 가로 3단: 원문(기본 30%, 접기 가능) | 쉬운 자료 캔버스(기본 44%, 종이 면) | 문장 도구(기본 26%, 최소 320px).
- 캔버스: 잠긴 안내 문구, 문서 제목, 구획 목차와 구획 제목, 카드(역할 라벨, 그림, 한 줄에 한 문장), 문장 상태 표시(대조 전 점, 근거 없음, AI 수정안), 수정안을 보는 문장의 점선 테두리, 용어 점선 밑줄.
- 선택: 문장을 누르면 선택하고, 카드 머리나 그림을 누르면 카드를 선택한다. ↑/↓ 이동, Enter 직접 수정, Esc 해제, ⌘Enter 대조 완료 후 다음 문장.
- 원문 연결: 선택하면 원문 칸이 첫 근거로 스크롤하고 모든 근거를 강조한다. "근거 1/2 ‹ ›"로 오간다. 원문의 강조를 누르면 연결된 문장을 선택한다. 원문에서 드래그로 선택하면 "선택한 문장의 근거로 추가" 버튼이 뜬다(한 문단 안에서만).
- 도구 칸(선택 없음): 문서 요약(대조 진행률, 근거 없는 문장, 마지막 점검 요약, 용어 목록과 편집·삭제).
- 도구 칸(문장 선택): 선택한 문장, 도구 5개, 도구 결과 영역, 원문 근거 인용(빼기), 이 문장의 점검 항목(점검 뒤 바뀌었으면 표시), [대조했어요].
- 도구 칸(카드 선택): 그림 바꾸기, 문장 추가, 카드 이동·삭제, 역할 표시.
- 더 쉽게 바꾸기: 수정안 1~3 탭, 전후 어절 차이, 숫자 변경 경고, [적용] / [고쳐서 적용] / [다시 제안] / [닫기]. 다른 문장을 선택하면 수정안은 닫힌다.
- 문장 나누기: "원래 1문장 → 새 N문장" 목록, 숫자 변경 경고, [적용] / [고쳐서 적용] / [닫기].
- 용어 설명 추가: 후보 용어 칩 또는 문장 속 드래그 선택 → 설명 초안 → 고친 뒤 [추가]. 이미 있는 용어면 편집으로 이어진다.
- 그림 바꾸기(카드 단위): 후보 4~6개(의미 설명 포함), [그림 없이], [내 그림 올리기] → 지금 그림과 나란히 비교 → 대체텍스트 확인 → [적용]. "글만" 설정이면 그림 기능을 숨긴다.
- 구조가 초안보다 새로우면 상단 배너와 [초안 다시 만들기].
- 검토에서 왔으면 [검토로 돌아가기].

**④ 검토하기**

- 상단: 고정 안내 한 줄, 요약(확인 필요 남음·살펴보기·처리함), 원문 대조 현황과 [대조하러 가기], [다시 점검], [검토 마치기].
- 왼쪽 목록: 묶음 제목 아래 항목 행. 필터(남은·처리한·전체)와 분류 칩. J/K 이동.
- 오른쪽 상세: 설명, 나란히 비교(쉬운 문장과 카드 라벨 | 원문 인용과 강조 | 그림이나 구조 값), 제안 수정안의 전후 차이, [수정안 적용] / [편집기에서 고치기] / [문제없음으로 확인](메모 선택).
- 처리한 항목은 흐리게 내려가고 다음 남은 항목을 선택한다.
- 들어올 때 마지막 점검의 내용 번호가 지금과 다르면 자동으로 다시 점검한다. 점검 중에는 이전 결과를 흐리게 보여 준다.
- [검토 마치기] 대화상자: 체크리스트(금액·날짜·기간 비교 / 인물 관계 / 그림과 글의 뜻(그림 사용 시) / 주장과 판단·결정의 구분), 남은 살펴보기 수와 대조하지 않은 문장 수. 남은 확인 필요가 0개이고 체크리스트를 모두 체크해야 완료할 수 있다.
- 항목이 없으면 "찾은 문제가 없어요. 그래도 체크리스트로 직접 확인해 주세요."라고 보여 준다. "통과", "정확함", "일치함" 같은 보증 표현은 쓰지 않는다.

**⑤ 미리보기**

- [읽기 화면] / [인쇄용] 탭. 읽기 화면은 휴대폰 390px, 태블릿 768px, 넓은 화면 프레임 안에서 실제 독자 화면 컴포넌트를 현재 문서로 그린다. 인쇄용은 실제 인쇄와 같은 A4 쪽을 줄여서 늘어놓고 전체 쪽수를 보여 준다.
- 상단에 검토 상태 배지, [편집으로], [내보내기로]. 편집 도구는 없다.

**독자 읽기 화면**

- 표지(제목, 한 줄 설명, 사건 정보, 긴 안내 문구, [읽기 시작]) → 구획 1~4 → 마침(긴 안내 문구, [처음으로]).
- 기본은 한 구획씩 넘기기다. 큰 [이전]/[다음], "2 / 4" 진행 표시(`aria-current`), ←/→ 키. [한 번에 모두 보기]로 바꿀 수 있다. 구획 화면 아래에 짧은 안내 문구를 둔다.
- 카드: 640px 미만은 그림 위, 이상은 그림 왼쪽. 본문 20px, 행간 1.7, `word-break: keep-all`. 글자 크기 3단계.
- 역할 라벨: "A씨가 한 말"(말풍선), "법원의 생각"(저울), "법원이 정한 것"(법봉). 호칭은 문서 설정을 따른다.
- 용어: 점선 밑줄을 누르면 설명이 뜬다(넓은 화면은 팝오버, 좁은 화면은 아래 시트).
- 없거나 비공개인 자료: "지금은 볼 수 없는 자료예요".

**인쇄**

- 인쇄 전용 화면이 게시본의 독자용 내용을 A4 쪽 컴포넌트로 그린다. 쪽 구성은 도메인의 쪽 채우기 결과를 쓰고, 미리보기의 인쇄용 탭과 같은 컴포넌트를 쓴다.
- 쪽: A4 세로, 여백 16mm. 표지(제목, 한 줄 설명, 사건 정보, 긴 안내 문구 상자) → 구획마다 새 쪽 → 카드(그림 약 35% 왼쪽, 본문 16pt·행간 1.6, 쪼개지지 않음) → 어려운 말 풀이 표. 모든 쪽 아래에 짧은 안내 문구와 "쪽 / 전체 쪽". 검토 전 게시본이면 모든 쪽 위에 "검토 전 초안 · 배포하지 마세요" 띠.
- 폰트와 그림이 모두 로드되면 인쇄 창을 연다. PDF 파일은 인쇄 창의 "PDF로 저장"으로 만든다. 서버가 생기면 같은 화면을 헤드리스 브라우저로 렌더링해 PDF 파일을 만들 수 있다.

**⑥ 내보내기**

- [PDF 저장]: 게시본을 만들고(같은 내용 번호면 재사용) 인쇄 전용 화면을 새 탭으로 연다. 검토 완료가 아니면 먼저 대화상자에서 [검토하러 가기] / [검토 전 초안으로 저장]을 고른다. 인쇄 창 안내 문구를 버튼 옆에 둔다.
- [읽기 화면 공개] 스위치: 검토 완료 상태에서만 켤 수 있다. 켜면 게시본을 만들거나 재사용해 공개 게시본으로 지정한다. 공개 중이면 주소, [주소 복사], [새 탭에서 열기], "v3 · 공개 시각"을 보여 준다. 더 새로 검토를 마친 문서가 있으면 [새 버전으로 바꾸기]를 보여 준다. 주소는 바뀌지 않는다.
- 게시본 이력: 번호, 시각, 검토 상태, 공개 중 표시, [PDF 다시 저장]. 현재 문서가 최신 게시본 이후 바뀌었으면 "게시본 이후 수정됨"을 표시한다.

### 디자인 시스템과 공유 컴포넌트

- 기존 shadcn(base-vega, Base UI), hugeicons, 토스증권 토큰, spring easing을 그대로 쓴다. 제작 도구는 사용자의 밝은·다크 테마를 따른다.
- **종이 면**: 편집 캔버스, 미리보기, 독자 화면, 인쇄물은 테마와 상관없이 밝은 종이 모양이다. 기존 토큰 체계 안에서 범위 한정 클래스로 토큰 값을 덮어쓴다. 컴포넌트에 색을 직접 쓰지 않는다.
- **자료 렌더러 하나**를 편집·읽기·인쇄 모드로 함께 쓴다. 카드, 문장, 용어 밑줄, 역할 라벨, 안내 문구의 모양이 한곳에서 정해진다.
- **원문 뷰어 하나**를 ②와 ③이 함께 쓴다. 구획 바로가기, 근거 강조, 드래그 선택 이벤트를 제공한다.
- **멀티스텝 로더**: Aceternity Multi Step Loader를 복사해서 고친다. 쓰지 않는 아이콘 의존성을 빼고 hugeicons로 바꾼다. 단계는 밖에서 넘겨받는 제어 방식이다. 색은 토큰으로 바꾼다. `role="status"`와 `aria-live`를 넣고, 움직임 줄이기 설정을 존중하고, 취소 버튼을 둔다. 단계는 약 1.5초마다 넘기다가 마지막 단계에서 응답을 기다린다.
- **안내 문구**는 프론트엔드 상수이며 문체별로 둔다.
  - 긴 문구(해요체): "이 자료는 판결 내용을 쉽게 설명하려고 만든 자료예요. 공식 판결문을 대신하지 않아요. 정확한 내용은 판결문 원문을 확인해 주세요."
  - 긴 문구(합니다체): "이 자료는 판결 내용을 쉽게 설명하기 위해 만든 자료입니다. 공식 판결문을 대신하지 않습니다. 정확한 내용은 판결문 원문을 확인해 주십시오."
  - 짧은 문구: "공식 판결문이 아닌 쉬운 설명자료예요" / "공식 판결문이 아닌 쉬운 설명자료입니다"
- 제작 UI 문구는 짧은 해요체다. AI 결과는 단정하지 않는다("달라 보여요", "확인해 주세요").

### 라이브러리

- 넣는 것: TanStack Query, TanStack Query Devtools(개발), zod(v4), zustand(v5), idb-keyval(목 저장소 전용), Vitest와 tsconfig 경로 플러그인(개발). 스크립트는 typecheck, test, test:watch를 더한다.
- 코드 복사: Aceternity Multi Step Loader(motion은 이미 있음).
- 넣지 않는 것:
  - React Hook Form: 오버스펙이다.
  - pdfcn: PDF 생성 전용이고, 1.0 이전이며, 한글 폰트 위험이 있고, 레이아웃을 두 번 만들어야 한다.
  - react-pdf: 원본 PDF 보기를 뺐다.
  - MSW: 엔드포인트를 지금 정하지 않는다.
  - diff 라이브러리: 도메인 함수로 충분하다.
  - jsdom과 Testing Library: 컴포넌트 테스트를 하지 않는다.

### 접근성, 오류, 성능

- 제작 화면은 WCAG 2.2 AA를 따른다: 키보드로 모든 기능, 보이는 포커스, 색만으로 구분하지 않기, 비동기 결과를 라이브 영역으로 알리기, 칸 크기 조절 손잡이의 키보드 조작.
- 독자 화면: 본문 20px 이상, 본문 대비 7:1 목표, 터치 영역 48px 이상, 모든 그림의 대체텍스트, 움직임 최소화, 구획 제목 구조. 인쇄물: 본문 16pt 이상, 색에 기대지 않는 라벨.
- 조회 중에는 레이아웃을 유지하는 스켈레톤을 보여 준다. 저장·도구·점검 실패는 토스트와 [다시 시도]로 알린다. 분석·초안 실패는 오류 상자를 띄운다. 없는 프로젝트와 없는 주소는 앱 모양의 404를 보여 준다.
- 가상 스크롤은 쓰지 않는다. 문장 단위 구독으로 다시 그리기를 줄인다.

## Testing Decisions

- **좋은 테스트**는 도메인 모듈의 공개 함수에 입력(프로젝트 요약, 구조, 문서, 텍스트, 높이 목록)을 주고 **밖에서 보이는 결과**만 확인한다. 함수 내부 구현, 스토어 구조, 컴포넌트 마크업은 검사하지 않는다. 테스트 이름은 제작자 관점의 규칙으로 쓴다(예: "AI 수정안을 적용하면 근거는 남고 대조 표시는 풀린다").
- **seam은 하나, 도메인 모듈이다.** TDD로 먼저 쓸 행동은 다음과 같다.
  - 단계 계산: 문서가 없을 때·있을 때의 진입 가능 여부, 검토 완료 뒤 내용이 바뀌면 "검토 후 수정됨", 최신 게시본과 내용 번호 비교, 이어서 할 단계
  - 초안 만들기 조건: 인물 없음, 결정 없음, 인물 없는 주장, 빈 문구, 확인 체크 없음, 남은 AI 표시 수
  - 구조 연산: 목록 사이 옮기기(근거 유지, 주장으로 옮길 때 인물), 근거 추가·빼기, 확인 표시 끄기가 수정 번호를 올리지 않음
  - 문서 연산: 직접 수정(출처와 대조), 수정안 적용(출처, 대조 해제, 근거 유지), 나누기 적용(순서, 근거 복사), 문장·카드 추가·삭제·이동의 경계(첫·끝 위치, 마지막 문장 삭제), 용어 추가 중복, 그림 바꾸기, 손본 문장 수
  - 되돌리기 이력: 50단계 상한, 새 변경 뒤 다시 하기 비움
  - 어절 차이와 숫자 변경 감지: 조사만 바뀐 경우, 문장부호, "1억 원"과 "100,000,000원" 동등, 날짜 표기
  - 용어 등장과 풀이 순서, 문서에 없는 용어
  - 독자용 내용 뽑기: 근거·대조·출처 제외, 대조만 바뀌면 내용이 같다고 판단
  - 쪽 채우기: 구획은 새 쪽, 카드는 쪼개지지 않음, 큰 블록은 혼자, 쪽 번호
  - 읽기 순서: 표지와 마침 포함, 그림을 쓰지 않는 설정
- 도구: Vitest(node 환경). 도메인 모듈 가까이에 테스트를 둔다.
- 기존 테스트가 없다. 이 작업의 도메인 테스트가 첫 사례다.
- 테스트하지 않는 것: React 컴포넌트, 목 어댑터 내부 규칙, Next 페이지. 각 구현 단위를 마칠 때마다 개발 서버를 띄워 브라우저에서 흐름을 직접 확인한다(콘솔 오류, 화면 구조, 상호작용, 스크린샷).
- 구현 단위마다 typecheck, lint, 관련 테스트 파일을 돌린다. 마지막에 전체 테스트, 빌드, 코드 리뷰를 한다.

## Out of Scope

- 서버 쪽 전부: 실제 AI, 실제 API와 엔드포인트, 인증과 권한, 실제 PDF 파일 생성, PDF 텍스트 추출.
- 협업: 공유 문서, 댓글, 동시 편집, 저장 충돌 처리.
- 스크린샷에만 있던 화면: 용어 사전 페이지, 설정 페이지, 카드뉴스 export, 도움말.
- 원본 PDF 보기, 스캔 PDF와 OCR, HWP 입력, 원문 안 검색.
- 편집: 끌어다 놓기, 구획 추가·순서 변경, 구획을 넘는 카드 이동, 게시본 비교·삭제·되살리기.
- 독자 화면: 읽어 주기(TTS), QR 코드, 다국어.
- 1024px 미만 화면에서 제작하기.
- 분석 도구와 로그 수집, E2E 테스트, 컴포넌트 단위 테스트.
- 대상 독자 선택(발달장애가 있는 성인으로 고정).

### 위험과 대응

- **화면 측정과 인쇄 결과가 어긋날 수 있다.** 쪽 크기를 mm 고정 컨테이너로 두고, 인쇄 CSS에서 브라우저 여백을 0으로 둔다. 미리보기와 인쇄가 같은 측정 결과를 쓰게 한다. Chrome에서 인쇄 결과를 직접 확인한다.
- **IndexedDB를 쓸 수 없는 환경**(일부 사생활 보호 모드)이 있다. 메모리 저장소로 바꾸고 "새로고침하면 데모 데이터가 사라져요"라고 알린다.
- **목 규칙이 제품 로직처럼 굳을 수 있다.** 목 모듈 밖에서 목 규칙을 import하지 못하게 한다. 서버 연동 때 모듈을 통째로 지운다.
- **Next.js 16의 바뀐 규칙**(Promise params, Suspense가 필요한 `useSearchParams`, 빌드 때의 사전 렌더링)은 단위마다 typecheck와 마지막 빌드로 확인한다.
